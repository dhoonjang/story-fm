# LLM 티어 · 캐싱 (LLM Tiers & Caching)

> 🚧 **초안 v0.2** · 2026-07-21 · [game-overview §9](./game-overview.md)의 심화
> — 티어 라우팅 · 멀티 프로바이더 · 멀티턴 캐시
>
> v0.1(비용 모델)에서 방향 전환 (결정 #12): **품질 우선, 비용 최적화는
> 후순위.** 비용 상한·압축 레벨 같은 절약 장치는 폐기하고, 역할별 모델
> 라우팅과 캐시 구조에 집중한다.

---

## 1. 방침

- **역할에 맞는 모델을 쓴다.** 절약을 위해 경험을 깎지 않는다 — 중계 상세도,
  개입 횟수, 서사 분량을 비용이 결정하는 일은 없다.
- 대신 **구조적 효율**은 설계에 넣는다: 멀티턴 캐시, 결과 캐싱, 컨텍스트
  위생. 이건 비용 절감이 아니라 **지연과 품질**을 위한 것이기도 하다.

## 2. 티어와 라우팅 (결정 #12)

| 티어 | 담당 | 모델 (스냅샷 2026-07-21) | 프로바이더 |
| --- | --- | --- | --- |
| **GM 티어** | 메인 서사 — 일상 스토리 전개, 의도 해석, **판정(장면 무관 고정)**, 서사 메모리·아크 운영, 페르소나 생성 | Claude Opus 계열 | Anthropic |
| **매치 티어** | 경기 진행 — `advance_match` 구간의 **경기 시뮬레이션**(사건 결정 + 중계 + 연출이 한 몸, `log_match_events` 기록 — 결정 #14), 정지점 연출, 경기 장면 대화 | **시작: Claude Opus** → DeepSeek V4 Pro (§3 검증 통과 후 전환) | Anthropic → DeepSeek |

- **GM은 단일 역할, 모델은 장면 라우팅.** 일상 장면은 GM 티어가, 경기 장면은
  매치 티어가 구동한다. 유저 입장에선 하나의 세계 — 티어 전환은 보이지 않는다.
- **판정은 GM 티어 고정** — 팀토크·면담·미디어의 `{outcome, intensity}` 판정
  기준이 장면에 따라 흔들리면 안 된다 (심판은 한 명).
- 모델 ID는 `packages/llm` 설정에서 단일 관리 — 문서·코드 하드코딩 금지
  (AGENTS.md 6-1). 위 모델명은 설계 스냅샷이다.

## 3. 멀티 프로바이더 추상화 (`packages/llm`)

```
GameLLM (공통 인터페이스)
 ├─ complete(context, tools, schema) — 티어 무관 공통 계약:
 │    tool call 스킬 호출 · Zod 구조화 출력 검증+재시도 · @문법 모델 턴
 ├─ AnthropicAdapter — 프롬프트 캐싱(cache_control 브레이크포인트) 처리
 └─ DeepSeekAdapter  — OpenAI 호환 API, 컨텍스트 캐싱(자동 프리픽스) 처리
```

- **출력 계약은 티어와 무관하게 동일하다**: 모델 턴 문법(→ [ai-manager
  §7](./ai-manager.md)), 스킬은 tool call, 구조화 출력은 Zod 검증 + 재시도
  (AGENTS.md 6-2). 어댑터가 프로바이더별 차이(캐시 지시자, tool call 포맷,
  시스템 프롬프트 규약)를 흡수한다.
- ⚠️ **프로토타입 1순위 검증 항목**: DeepSeek의 tool call 안정성 · 한국어
  서사 품질 · `@문법` 준수. 미달 시 경기 장면도 GM 티어로 폴백 — 라우팅
  설정 한 줄로 가능해야 한다 (폴백 경로를 처음부터 설계).

## 4. 멀티턴 캐시 구조

캐싱은 **프리픽스 매치** — 앞이 1바이트라도 바뀌면 뒤가 전부 무효. GM
컨텍스트 층(→ ai-manager §4)을 **안정도 순서**로 쌓는다: 자주 바뀌는 것일수록 뒤로.

| 순서 | 층 | 변경 빈도 | 비고 |
| --- | --- | --- | --- |
| 1 | 시스템 (GM 규칙·문법·세계관) | 불변 | **날짜·ID 인터폴레이션 금지** |
| 2 | 페르소나 정적부 (핵심 NPC 프로필) | 드묾 | |
| 3 | 세계 스냅샷 | 상태 변경 시 | tick·스킬마다 갱신 — 여기부터 재캐시 감수 |
| 4 | 서사 메모리 발췌 · 최근 대화 | 매 턴 | 멀티턴 패턴: 마지막 턴 뒤에 이어붙임 |

- **Anthropic (GM 티어)**: `cache_control` 브레이크포인트를 ①시스템
  ②페르소나 정적부에, 멀티턴은 마지막 턴에. 모델별 최소 캐시 프리픽스
  (2~4k tok) 이상이 되도록 1~2층을 구성.
- **DeepSeek (매치 티어)**: 컨텍스트 캐싱이 프리픽스 기반 자동 — 명시
  브레이크포인트는 없지만 **같은 원칙(안정도 순서)이 그대로 적용**된다.
- **장면 전환 = 캐시 분리**: 경기 진입 시 매치 티어의 프리픽스(경기용 시스템
  + StrengthPacket + 스쿼드 스냅샷 + **등장 페르소나**(수석코치·출전/벤치
  핵심) + **경기 관련 서사 메모리 발췌** + 일상 맥락 요약 — 구성은
  match-sim §2)를 새로 쌓고 경기 내내 재사용. 경기 종료 시 결과 요약이 GM
  티어 컨텍스트로 돌아온다 (핸드오프 → §7).

## 5. 결과 캐싱 — 재호출 자체를 없앤다

- 스카우트 리포트·상대 프리뷰: 입력 상태가 같으면 저장본 재사용.
- 페르소나: 1회 생성 후 고정 (→ personas §4). 새 게임 준비의 대량 생성은
  비실시간이므로 Batch 처리 가능.

## 6. 계측

- 모든 호출에 `{scene, tier, skill?}` 태그 + usage 로깅.
- **캐시 히트율이 1순위 지표** — 0에 가까우면 프리픽스에 조용한 무효화
  요인(타임스탬프, 비결정적 직렬화)이 있다는 신호.
- 비용은 모니터링만 한다 — 게임 동작에 개입시키지 않는다 (상한·압축 없음).

## 7. 미해결

- DeepSeek 어댑터 검증 (tool call · 한국어 · @문법) — §3
- 장면 전환 핸드오프 — 일상 맥락을 경기 프리픽스에 얼마나 요약해 넘길지,
  경기 결과를 일상 컨텍스트로 어떻게 되돌릴지

  (지연 ↓ vs 판정 일관성 ↑)
