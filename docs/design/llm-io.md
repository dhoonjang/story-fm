# LLM 입출력 구성 (메인 채팅 · 경기 진행)

> 📐 **구현 기준 문서** · 2026-07-25 작성, 캐시 계층·안개·조회 도구 도입으로 전면 개정.
> 코드 기준: `packages/agents/src/gm.ts`, `packages/llm/src/anthropic-adapter.ts`,
> `packages/engine/src/{scouting,lookup}.ts`. 프롬프트·컨텍스트·도구가 바뀌면 이 문서를 함께 갱신한다.

story-fm의 LLM 호출은 **두 역할**뿐이다. 둘은 같은 함수(`runRealGmTurn`)에서
`state.phase`로 라우팅되고, 시스템 블록·상태 스냅샷·이력만 갈린다.

| 역할 | 조건 | 시스템 프롬프트 | 티어 |
| --- | --- | --- | --- |
| **GM** (메인 채팅) | `phase !== "match"` | `GM_SYSTEM` | `TIERS.gm` |
| **매치 캐스터** (경기 진행) | `phase === "match"` | `MATCH_CASTER_SYSTEM` | `TIERS.match` |

모델 ID는 `packages/llm/src/config.ts`가 단일 관리한다 (현재 두 티어 모두
`claude-opus-4-8`, `max_tokens: 4096`, `thinking: { type: "adaptive" }`).

> **`phase`는 라우팅 전용이다.** 어떤 프롬프트·컨텍스트를 쓸지 고르는 스위치이고,
> 모델 입력에는 절대 넣지 않는다. 모델이 알아야 할 국면("프리시즌", "오늘 경기일")은
> 일정·이적창 문장이 자연어로 전달한다. `idle`/`matchday` 같은 내부 enum이
> 서사로 새는 경로를 원천 차단한다.

## 1. 입력의 3층 구조 (가장 중요)

입력은 **변경 빈도** 순으로 3층이다. 앞 두 층은 프롬프트 캐시에 올라가 read 단가
(0.1×)로 읽히고, 마지막 층만 매 턴 정가로 읽힌다.

```
┌─ ① 고정 ────────────── tools 정의 → system 블록 1 ──── [캐시 브레이크포인트]
│  세이브와 무관. 배포될 때까지 바이트 단위로 동일.
├─ ② 레퍼런스 ────────── system 블록 2 ─────────────── [캐시 브레이크포인트]
│  세이브마다 다르지만 거의 안 바뀜 (이적·킥오프 때만).
├─ ③ 이력 ────────────── messages[0..n-1] ──────────── [증분 브레이크포인트]
│  지난 턴들. 한번 쓰이면 불변 → 턴이 쌓일수록 캐시가 커진다.
└─ ④ 이번 턴 ──────────── user 발화 + role:"system" 상태 스냅샷 ── 캐시 밖
   매 턴 바뀌는 것만. 실측 300~400 토큰.
```

### 왜 이렇게 나누는가

프롬프트 캐시는 **프리픽스 바이트가 완전히 일치**해야 적중한다. 그래서 배치가
곧 비용이다. 개정 전에는 브레이크포인트가 `system` 하나뿐이어서, 이력과 컨텍스트
전체(약 2,700 토큰)를 매 턴 정가로 다시 읽었다. 개정 후 매 턴 새로 읽는 양은
**300~400 토큰**이다.

이 구조를 지키는 규칙 세 가지:

1. **휘발성 값을 앞 층에 넣지 마라.** 날짜·순위·잔고가 레퍼런스 블록에 섞이면
   매 턴 프리픽스가 달라져 캐시가 전부 죽는다. (테스트가 이걸 지킨다 —
   `gm-input.test.ts`의 "휘발성 값이 새지 않는다")
2. **순서를 흔들지 마라.** 명부는 (포지션, id)로 정렬한다. OVR처럼 훈련으로
   바뀌는 값으로 정렬하면 순서가 흔들려 캐시가 깨진다.
3. **도구 목록을 턴마다 바꾸지 마라.** 도구는 프리픽스의 맨 앞이라, 하나만
   추가·제거해도 전체 캐시가 무효화된다. GM 티어와 경기 티어는 도구 집합이
   달라 각자 캐시를 갖는다 (경기 티어에만 `log_match_events`).

### 실측 (Opus 4.8, `count_tokens`·`usage` 기준)

| 구간 | 토큰 | 캐시 |
| --- | ---: | --- |
| tools 16개 정의 | ~3,400 | ✅ ① |
| `GM_SYSTEM` | ~1,900 | ✅ ① |
| 레퍼런스(감독 + 선수 명부 30명) | ~800 | ✅ ② |
| 이력 (턴마다 증가) | 가변 | ✅ ③ |
| 상태 스냅샷 + 감독 발화 | **300~400** | ❌ ④ |
| (경기) 전력 분석 패킷 | ~2,400 | ✅ ② |
| (경기) 장부 스냅샷 + 발화 | **~1,000** | ❌ ④ |

⚠️ **Opus 4.8의 최소 캐시 프리픽스는 4,096 토큰이다.** 미달이면 에러 없이
조용히 캐시가 꺼진다. ①이 현재 5,300 토큰이라 여유가 있지만, 도구를 대량
삭제하거나 프롬프트를 크게 줄일 때는 이 하한을 확인해야 한다.

실제 턴에서 확인한 값 (실모드 5턴):

```
턴1  정가 378 · 캐시read 14,997 · 캐시write 8,717
턴2  정가 312 · 캐시read 32,398 · 캐시write 2,820
턴3  정가 298 · 캐시read 26,115 · 캐시write 2,129
```

캐시read가 큰 것은 한 턴이 도구 루프로 여러 요청을 돌기 때문이다(반복마다
프리픽스를 다시 읽는다). **정가 토큰이 300대에 머무는 것**이 이 설계의 지표다.
`GmTurnResult.usage`로 관측할 수 있고, `cacheReadTokens`가 0에 머물면 캐시 계층이
깨진 것이다.

## 2. 공통 호출 계약 (`AnthropicGameLLM.runTurn`)

### 입력 (`TurnRequest`)

```
system    : string | string[]   // 배열이면 앞이 더 안정적인 순서. 블록마다 브레이크포인트
history   : MessageParam[]      // 이전 턴 이력 (thinking·tool_use 블록까지 원형 보존)
user      : string              // "[감독]\n<발화>"
stateNote?: string              // 휘발성 상태 — messages 끝에 role:"system"으로
tools     : GameToolSpec[]      // JSON Schema + Zod + 엔진 스킬 핸들러 (readOnly 플래그)
onText?   : (delta) => void     // 주면 스트리밍 모드
maxTokens?
```

Anthropic 요청 조립:

```
tools    = tools.map(...)                                   // 프리픽스 맨 앞
system   = system.map(text => ({ type:"text", text, cache_control:{type:"ephemeral"} }))
messages = [ ...정규화된 이력(마지막에 브레이크포인트),
             { role:"user",   content: user },
             { role:"system", content: stateNote } ]         // 있을 때만
```

### 상태 스냅샷을 왜 `role:"system"`으로 보내는가

Opus 4.8은 `messages` 배열에 `role:"system"` 항목을 허용한다(베타 헤더 불필요).
셋 다 얻는다.

- **캐시 보존** — 최상단 `system`을 매 턴 고쳐 쓰면 그 뒤 전체가 무효화된다.
  끝에 붙이면 앞 프리픽스가 그대로 살아 있다.
- **역할 분리** — 상태를 감독 발화에 섞으면 모델이 "감독이 자기 팀 재정을
  읊었다"로 읽는다. 오퍼레이터 채널은 그런 오독을 만들지 않는다.
- **위조 불가** — 유저 텍스트 안의 지시문과 달리 스푸핑되지 않는 경로다.

제약과 대응:
- `messages[0]`이 될 수 없고, 유저 메시지 뒤에 와야 한다 → 항상 발화 다음에 붙인다.
- 미지원 모델은 400을 던진다 → 어댑터가 **한 번 감지하면 모델별로 기억**하고
  이후엔 `상태\n\n발화` 형태로 유저 메시지에 접어 넣는다 (DeepSeek 전환 대비).
- **이력에 남기지 않는다.** 매 턴 새로 주입되므로 누적되면 지난 날짜·지난
  스코어가 이력에 쌓여 모델을 혼란시킨다. `runTurn`이 반환 이력에서 걷어낸다.

### 도구 루프

1. 응답 `content`의 **text 블록**을 이어붙여 서사 텍스트로 누적한다.
2. `assistant` 메시지를 **content 전체(thinking 포함)** 그대로 이력에 push한다.
3. `stop_reason !== "tool_use"` 면 종료.
4. `tool_use` 블록마다 → `spec.handle(input)`:
   - Zod 검증 실패 → `{ ok:false, message:"입력 오류 — …" }`
   - 엔진 스킬/조회 실행 → `{ ok, message }`
   - 결과를 `tool_result`(내용 = 한국어 message, `is_error = !ok`)로 되돌린다 → 모델이 스스로 수정 재시도.
5. 최대 **8회 왕복**(`MAX_TOOL_ITERATIONS`). 조회 + 실행이 한 턴에 같이 도므로
   개정 전 6회에서 늘렸다. 반복마다 브레이크포인트를 직전 메시지로 옮겨 루프
   안에서도 증분 캐시가 걸린다.

### 이력 위생 (필수)

- **정규화** — 문자열 content를 텍스트 블록으로 통일한다. 어떤 턴엔 문자열,
  다른 턴엔 블록으로 같은 메시지를 보내면 프리픽스 바이트가 달라져 매 턴
  캐시가 깨진다.
- **마커 비오염** — `cache_control`은 요청용 복사본에만 붙인다. 원본 이력에
  남으면 세이브에 누적되고, 다음 턴 요청이 브레이크포인트 상한(4개)을 넘겨
  400이 된다.
- **미해결 tool_use 마감** — 턴이 `max_tokens` 등으로 끊겨 마지막 assistant에
  미해결 `tool_use`가 남으면 합성 `tool_result`(is_error)로 닫는다. 닫지 않으면
  이 이력을 재사용하는 다음 요청이 400으로 죽어 경기가 복구 불능이 된다.

### 출력 (`TurnResult`)

```
text          // 텍스트 블록 연결 (@문법 서사)
history       // 갱신된 이력 (role:"system" 제외) — 다음 턴에 그대로 넘긴다
usage         // input / output / cacheRead / cacheWrite 토큰 누적
toolCallCount
stopReason
```

## 3. 메인 채팅 (GM 티어)

### ① 고정 — `GM_SYSTEM`

출력 문법(@화자), 철칙 6개, 조회 규약, 안개 규약, 진행·훈련·전술 규약, 언어
(한국어 · **능력치 숫자 낭독 금지**, 결정 #2).

철칙 5가 이번 개정의 핵심이다. 개정 전 "조회 질문은 컨텍스트로 즉답한다 — 도구
불필요"는 **컨텍스트에 없는 것을 지어내라는 지시**였다. 지금은 뒤집혀 있다:

> **모르는 것을 지어내지 마라.** 주어지는 것은 스쿼드 명부와 상태 요약뿐이다.
> 그 밖의 사실 — 능력치·컨디션·계약·성장, 타 팀 선수, 순위표, 일정 — 은
> 반드시 조회 도구로 확인한 뒤 답하라.

### ② 레퍼런스 — `buildGmReference(state)`

| 내용 | 변경 시점 |
| --- | --- |
| 감독 프로필 (배경 · 능력 4축 · 평판 3축) | 레벨업·평판 변동 |
| 우리 팀 선수 명부 — `id\|이름\|주포지션` 전원 (30~34명) | 이적·유스 승격·포지션 변경 |

**능력치를 일부러 넣지 않는다.** GM이 매 턴 필요한 것은 "누가 우리 팀에 있고
도구에 어떤 id를 넣어야 하는가"다. 수치는 물어볼 때만 조회하면 된다. 이 결정으로
개정 전 상위 18명 표(1,461 토큰)가 전원 명부(800 토큰)로 바뀌면서 **정보량은
늘고 토큰은 줄었다**.

### ③ 이력 — `buildGmHistory(state)`

`state.chat`에서 **텍스트만** 재구성한다(도구 호출 기록 제외). 마지막 항목은
방금 push된 이번 발화이므로 뺀다.

창은 12턴 이상 유지하되 **시작점을 6턴 단위로만 옮긴다.** 매 턴 한 칸씩
미끄러지면 프리픽스가 계속 달라져 이력 캐시가 한 번도 적중하지 않는다. 6턴
동안 시작점을 고정하면 그 구간 내내 캐시가 살아 있다.

### ④ 이번 턴 — 발화 + `buildGmStateNote(state)`

```
[상태 스냅샷 — 이 블록은 매 턴 갱신된다]
2026-07-26 (일) · 시즌 1 · 리그 1위 · 프리시즌 (개막 2026-08-15) · 여름 이적시장 열림 (~2026-09-01)
다음 경기: R1 2026-08-15 홈 vs 사우샘프턴
전술: 4-3-3 · 멘탈3 라인3 압박3 템포3 폭3 패스mixed · 선발 평균 적응 60
재정: 잔고 £120.0M · 주급 £3.42M/주 · 이적예산 £90.0M
예정 훈련 2건: 07-27 오전 세트피스 반복 / 07-28 오후 회복 러닝
주의: 부상 1 (사카 햄스트링~08-02) · 불만 1 (외데고르) · 미토마 스카우트 파견 중 — 보고 08-02
최근 사건: 07-01 여름 이적시장 개장 / …
```

감독 발화는 `[감독]\n<원문>`으로 따로 간다.

### 도구 (16개 = 실행 11 + 조회 4 + 스카우트 1)

**실행 (상태 변경 — 채팅에 스킬 칩으로 기록)**

| 도구 | 엔진 스킬 | 비고 |
| --- | --- | --- |
| `advance_time` | `advanceTime` | 시간이 흐르는 유일한 경로. digest를 message로 반환 |
| `start_match` | `startMatch` | 경기일에만 |
| `set_lineup` | `setLineup` | `starting[11]{playerId, position?}` + `bench[]` |
| `set_captain` | `setCaptain` | |
| `set_tactics` | `setTactics` | 경기 중이면 `refreshPacket`까지 |
| `set_player_instruction` | `setPlayerInstruction` | 배치에 저장 |
| `set_training` | `setTraining` | `sessions[] / repeatWeekly[] / weeks / clear` → 일정 엔트리 생성 |
| `team_talk` | `applyTeamTalk` | 판정형 — LLM은 `outcome·intensity`만, 변화량은 공식 |
| `talk_to_player` | `applyTalkToPlayer` | 판정형 + 불만 해소 |
| `substitute` | `substitutePlayer` | 경기 중 |
| `apply_narrative_event` | `applyNarrativeEvent` | 사기·폼만, 한도 내, 일 3회 |
| `scout_player` | `scoutPlayer` | 스카우트 파견 (안개 해제 예약) |

**조회 (읽기 전용 — `readOnly: true`, 칩으로 기록하지 않는다)**

| 도구 | 엔진 | 반환 |
| --- | --- | --- |
| `search_players` | `searchPlayers` | 팀·포지션·나이·이름 필터 + 정렬, 상한 8(최대 15). 넘치면 남은 인원 수를 알린다 |
| `get_player` | `playerCard` | 선수 카드 — 우리 팀은 전부, 타 팀은 안개 적용 |
| `get_team` | `teamProfile` | 순위·전적·전술·최근 5경기·주력 선수 + 상대 전적 (경기 전 스카우팅 리포트) |
| `get_league` | `leagueView` | `standings` 20팀 / `fixtures` 지난·예정 |

조회를 칩으로 남기지 않는 이유: 상태를 바꾸지 않는 호출이 채팅을 덮으면 감독이
정작 중요한 실행 칩(라인업 변경·훈련 등록)을 놓친다.

**도구 설명은 "언제 호출하는가"를 쓴다.** Opus 4.8은 도구를 보수적으로 집기
때문에, 기능 설명만 있는 description은 호출률이 떨어진다.

### 출력

- **텍스트**: `@화자:` 줄들. 후처리로 `humanizePlayerIds`가 서사에 흘러든 선수
  id를 이름으로 치환한다(유저에게 id 노출 금지).
- **도구 호출 기록**: `{ name, summary(=엔진 메시지), input }` → `chat[].toolCalls`에
  저장되고 UI가 스킬 칩으로 렌더(클릭 시 input 상세). 조회는 제외.
- **저장**: `chat`에 `{ role:"model", text, toolCalls, at: 게임날짜 }` push → `saveGame`.

### 스트리밍 · 원자성 (`runTurnLocked`)

- 게임 id별 **뮤텍스**로 턴·라인업 편집을 직렬화(저장 경합 방지).
- `onDelta` → NDJSON: `{"type":"delta","text":…}` … `{"type":"done","payload":…}`.
- GM 턴이 예외로 실패하면 **턴 시작 시점 백업(structuredClone)으로 롤백**하고
  사과 메시지만 남긴다(부분 커밋 방지).

### 클라이언트 파싱

`^@([^:]*):\s?(.*)$` 로 화자/대사를 분리, `*별표*`는 연출로 렌더. 스트리밍 중
`@화자`의 콜론이 아직 안 온 마지막 줄은 다음 델타까지 보류(파싱 깨짐 방지).

## 4. 경기 진행 (매치 캐스터 티어)

같은 3층 구조를 쓰고 내용만 갈린다.

| 층 | 내용 |
| --- | --- |
| ① 고정 | `MATCH_CASTER_SYSTEM` — 출력 문법, 경기 규칙 6개(패킷이 유일한 판단 근거 · 서사에 등장한 사건은 반드시 기록 · 시간은 앞으로만 · 오류 수정 재기록 · 우위는 확률적 · 골 남발 금지), 진행 방식(한 턴 = 다음 정지점까지), 대화 규칙, 언어 |
| ② 레퍼런스 | **전력 분석 패킷 JSON** — 킥오프에 고정. 존 전력·매치업·키포인트·기대득점·업셋확률·라인업 |
| ③ 이력 | `state.pendingMatch.casterHistory` — 경기 내내 누적되는 Anthropic 이력 원형(thinking·tool_use·tool_result 포함). 세이브에 직렬화되므로 저장/로드 후에도 경기를 이어간다 |
| ④ 이번 턴 | `buildLedgerNote(state)` (role:"system") + 감독 발화 |

패킷을 캐시 블록으로 올린 것이 경기 티어의 핵심 개선이다. 패킷은 3,600자
(~2,400 토큰)인데 킥오프 이후 `set_tactics`/`substitute` 때만 갱신된다. 매 턴
정가로 다시 읽을 이유가 없다. 갱신되면 ②가 한 번 무효화되지만, 그건 감독이
전술을 바꾼 순간이니 대가로 적절하다.

장부 스냅샷:

```
[경기 장부 — 매 턴 갱신]
스코어 1:0 · 28′ · first_half
홈 온필드: arsenal-raya(다비드 라야), … (id(이름) 병기)
홈 벤치: … (교체 0/5, 기회 0/3)
어웨이 온필드/벤치: …
퇴장: …                                    // 있을 때만
```

`id(이름)` 병기가 캐스터가 **서사엔 이름, 도구엔 id**를 쓰게 하는 근거다.

### 도구

GM 도구 16개 **+ `log_match_events`**. 이벤트 배열을 받아 `applyEvents`(packages/sim)가
검증한다:

- 온필드가 아닌 선수의 골/카드 → 반려
- 장부 현재 분보다 과거 → 반려
- 하드 상한: 팀당 6골, 배치당 20이벤트, 교체 5회·윈도 3회
- 반려 메시지가 `is_error`로 되돌아가 캐스터가 사건을 고쳐 재기록

### 종료 처리

장부 `phase === "finished"` 가 되면 **`finalizeMatch`가 자동 실행** — MATCH 결과
기록(**양 팀 출전 명단 포함**), 일정 엔트리 done, 출전/득점(SEASON_STAT), 피로·사기·폼,
전술·포지션 적응도 상승(+GROWTH 로그), BOOKING→SUSPENSION, 경기 부상(INJURY),
홈 입장 수입(LEDGER), 평판·감독 XP, 서사 노트.

출전 명단을 남기는 이유는 스카우팅이다 — "감독이 직접 뛰는 걸 본 선수"의 유일한 근거.

## 5. 정보 비대칭 (안개)

`packages/engine/src/scouting.ts`가 단일 소스. **선수 단위** 4단계다.

| 수준 | 조건 | 능력치 | 잠재력 |
| --- | --- | --- | --- |
| `own` | 우리 팀 선수 | 정확 (숫자) | 공개 |
| `scouted` | 스카우트 리포트 완료 | 정확 (숫자) | **미지** |
| `seen` | 우리와의 경기에 **실제로 출전**한 걸 봤다 | ±3 오차, 라벨만 | 미지 |
| `rumoured` | 그 외 (리그 평판) | ±6 오차, 라벨만 | 미지 |

- **지식 수준은 저장하지 않는다.** MATCH 출전 명단과 SCOUT_REPORT에서 파생한다
  (v6의 파생 우선 원칙). 벤치에만 앉아 있던 선수는 `seen`이 되지 않고, 우리가
  뛰지 않은 경기의 선수도 되지 않는다.
- **오차는 결정적이다.** `hash(seed, playerId, 능력치)`로 세이브 안에서 고정된
  오프셋을 만든다. 호출마다 새로 뽑으면 GM이 어제 한 말과 오늘 한 말이 달라져
  스카우팅 정보 자체를 신뢰할 수 없게 된다.
- **표현 계층 전용.** 코어(장부·판정·전력 패킷)는 언제나 참값으로 계산한다.
  관측값이 게임 상태에 반영되는 경로는 없다.
- 안개가 낀 선수에게는 **숫자를 아예 주지 않는다** — `월드클래스 / 리그 최정상 /
  정상급 / 준주전급 / 리그 평균 / 평균 이하 / 약점` 라벨과 강점·약점 지목만.
  숫자를 주면 모델이 그대로 읊고 유저가 정확값으로 오해한다.
- 공개 정보는 지식 수준과 무관하게 정확하다: 이름·나이·소속·주포지션·시즌
  출전·득점·계약 만료·부상 여부.

`scout_player`로 파견하면 `SCOUT_DAYS` 뒤 tick이 완료 처리하고 다이제스트로
보고한다. 동시 파견은 `SCOUT_CONCURRENT_LIMIT`명까지.

## 7. 알려진 공백 (다음 마일스톤 후보)

1. **토큰 예산 상한 미구현** — usage는 관측 가능해졌지만 상한·경고는 없다.
2. **매치 티어가 도구 루프 상한을 자주 소진한다.** 실측에서 킥오프 턴이 8회
   왕복을 모두 썼다(성공 기록 3건 + 반려 재시도). 캐스터가 사건을 잘게 쪼개
   기록하기 때문인데, 반려 사유 분포를 봐야 프롬프트로 줄일지 상한을 올릴지
   판단할 수 있다.
3. **티어 분리(경기=DeepSeek)는 설정만 있고 미적용** (결정 #12). 전환 시
   `role:"system"` 폴백 경로가 실제로 쓰인다.
4. **조회 도구에 재정 상세가 없다.** 잔고·주급·예산은 상태 스냅샷에 있고 월별
   원장은 오피스 뷰에만 있다. GM이 월별 지출을 논해야 하면 도구를 추가한다.
5. **mock GM은 조회를 흉내내지 않는다.** e2e는 실행 스킬 경로만 검증한다.
