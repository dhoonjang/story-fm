# LLM 입출력 구성 (메인 채팅 · 경기 진행)

> 📐 **구현 기준 문서** · 2026-07-28 갱신, 멀티 프로바이더 어댑터 반영.
> 코드 기준: `packages/agents/src/gm.ts`, `packages/llm/src/{game-llm,factory,anthropic-adapter,gemini-adapter}.ts`,
> `packages/engine/src/{scouting,lookup}.ts`. 프롬프트·컨텍스트·도구가 바뀌면 이 문서를 함께 갱신한다.

story-fm의 LLM 호출은 **두 역할**뿐이다. 둘은 같은 함수(`runRealGmTurn`)에서
`state.phase`로 라우팅되고, 시스템 블록·상태 스냅샷·이력만 갈린다.

| 역할                        | 조건                | 시스템 프롬프트       | 티어          |
| --------------------------- | ------------------- | --------------------- | ------------- |
| **GM** (메인 채팅)          | `phase !== "match"` | `GM_SYSTEM`           | `TIERS.gm`    |
| **매치 캐스터** (경기 진행) | `phase === "match"` | `MATCH_CASTER_SYSTEM` | `TIERS.match` |

모델 ID는 `packages/llm/src/config.ts`가 단일 관리한다. 코드 기본값은 두 티어
모두 `claude-opus-4-8`이고, 배포 환경에서 `LLM_PROVIDER=google`로 바꾸면 두
티어 모두 `gemini-3.6-flash`를 사용한다. 유저에게 모델 선택 UI는 노출하지 않는다.
인증은 Anthropic이 `ANTHROPIC_API_KEY`, Gemini가 `GOOGLE_API_KEY` 또는
`GEMINI_API_KEY`를 사용한다.

```bash
# 코드 기본값: Anthropic
ANTHROPIC_API_KEY=... pnpm dev

# Gemini로 전환
LLM_PROVIDER=google GOOGLE_API_KEY=... pnpm dev
```

`LLM_PROVIDER`는 프로세스 시작 시 읽으므로 변경 후 서버를 다시 시작한다.

두 시스템 프롬프트의 코드 상수는 **기본값**이다. 어드민 `/admin/prompts`에서
편집하면 `.data/system-prompts.json`에 오버라이드가 저장되고, 다음 실모드 턴부터
모든 게임에 즉시 적용된다. 파일이 없거나 어드민에서 초기화하면 코드 기본값으로
돌아간다. 프롬프트 변경은 ① 고정 프리픽스 자체가 바뀌는 일이므로 기존 프롬프트
캐시는 무효화되고 새 프리픽스로 다시 형성된다. mock 모드는 규칙 기반이라 영향을
받지 않는다.

스킬 설명은 시스템 프롬프트에 중복해 넣지 않는다. 도구 JSON Schema와 함께
모델에 전달되는 `description`을 `packages/agents/src/skill-descriptions.ts`에서
단일 관리하고, 같은 어드민 화면에서 스킬별로 편집한다. 편집본은
`.data/skill-descriptions.json`에 저장된다. 설명만 편집할 수 있고 도구 이름,
입력 스키마, 실행 함수, 읽기 전용 여부는 코드 계약이라 어드민에서 바꿀 수 없다.
스킬 설명 변경도 tools 프리픽스가 달라지는 일이므로 해당 캐시는 다시 형성된다.

> **`phase`는 라우팅 전용이다.** 어떤 프롬프트·컨텍스트를 쓸지 고르는 스위치이고,
> 모델 입력에는 절대 넣지 않는다. 모델이 알아야 할 국면("프리시즌", "오늘 경기일")은
> 일정·이적창 문장이 자연어로 전달한다. `idle`/`matchday` 같은 내부 enum이
> 서사로 새는 경로를 원천 차단한다.

## 1. 입력의 4층 구조 (가장 중요)

입력은 **변경 빈도** 순으로 쌓는다. 논리적 4층은 제공자 공통이다. Anthropic은
앞 세 층에 명시적 캐시 브레이크포인트를 두고, Gemini는 같은 안정 프리픽스를
implicit caching 대상으로 보낸다. 캐시 할인 방식과 적중 하한은 제공자별이다.

```
┌─ ① 고정 ────────────── tools 정의 → system 블록 1 ──── [안정 프리픽스]
│  세이브와 무관. 배포될 때까지 바이트 단위로 동일.
├─ ② 레퍼런스 ────────── system 블록 2 ─────────────── [안정 프리픽스]
│  세이브마다 다르지만 거의 안 바뀜 (이적·킥오프 때만).
├─ ③ 이력 ────────────── messages[0..n-1] ──────────── [제공자 원형 보존]
│  지난 턴들. 한번 쓰이면 불변 → 턴이 쌓일수록 캐시가 커진다.
└─ ④ 이번 턴 ──────────── user 발화 + 휘발 상태 스냅샷 ────────── 캐시 밖
   매 턴 바뀌는 것만. 실측 300~400 토큰.
```

### 왜 이렇게 나누는가

프롬프트 캐시는 공통 프리픽스가 길고 안정적일수록 적중한다. 그래서 배치가 곧
비용이다. Anthropic 실측에서는 개정 후 매 턴 새로 읽는 양이 300~400 토큰이다.
Gemini의 implicit cache는 같은 순서 원칙을 사용하지만 동일한 수치·단가를
보장하지 않으며 `cachedContentTokenCount`를 관측한다.

이 구조를 지키는 규칙 세 가지:

1. **휘발성 값을 앞 층에 넣지 마라.** 날짜·순위·잔고가 레퍼런스 블록에 섞이면
   매 턴 프리픽스가 달라져 캐시가 전부 죽는다. (테스트가 이걸 지킨다 —
   `gm-input.test.ts`의 "휘발성 값이 새지 않는다")
2. **순서를 흔들지 마라.** 명부는 (포지션, id)로 정렬한다. OVR처럼 훈련으로
   바뀌는 값으로 정렬하면 순서가 흔들려 캐시가 깨진다.
3. **도구 목록을 턴마다 바꾸지 마라.** 도구는 프리픽스의 맨 앞이라, 하나만
   추가·제거해도 전체 캐시가 무효화된다. GM 티어와 경기 티어는 도구 집합이
   달라 각자 캐시를 갖는다 (경기 티어에만 `log_match_events`).

### 실측 (Opus 4.8, `count_tokens`·`usage` 기준)

| 구간                            |        토큰 | 캐시 |
| ------------------------------- | ----------: | ---- |
| tools 16개 정의                 |      ~3,400 | ✅ ① |
| `GM_SYSTEM`                     |        ~700 | ✅ ① |
| 레퍼런스(감독 + 선수 명부 30명) |        ~800 | ✅ ② |
| 이력 (턴마다 증가)              |        가변 | ✅ ③ |
| 상태 스냅샷 + 감독 발화         | **300~400** | ❌ ④ |
| (경기) 전력 분석 패킷           |      ~2,400 | ✅ ② |
| (경기) 장부 스냅샷 + 발화       |  **~1,000** | ❌ ④ |

⚠️ **Opus 4.8의 최소 캐시 프리픽스는 4,096 토큰이다.** 미달이면 에러 없이
조용히 캐시가 꺼진다. 간소화 후 tools + `GM_SYSTEM`은 이 하한에 가까우므로,
스킬 설명이나 프롬프트를 더 줄일 때는 `count_tokens`로 다시 확인해야 한다.

실제 턴에서 확인한 값 (실모드 5턴):

```
턴1  정가 378 · 캐시read 14,997 · 캐시write 8,717
턴2  정가 312 · 캐시read 32,398 · 캐시write 2,820
턴3  정가 298 · 캐시read 26,115 · 캐시write 2,129
```

캐시read가 큰 것은 한 턴이 도구 루프로 여러 요청을 돌기 때문이다(반복마다
프리픽스를 다시 읽는다). **정가 토큰이 300대에 머무는 것**이 이 설계의 지표다.
`GmTurnResult.usage`로 관측할 수 있고, `cacheReadTokens`가 0에 머물면 캐시 계층이
깨진 것이다.

## 2. 공통 호출 계약 (`GameLLM.runTurn`)

### 입력 (`TurnRequest`)

```
system    : string | string[]   // 배열이면 앞이 더 안정적인 순서
history   : TextMessage[] | StoredLlmHistory | legacy unknown[]
user      : string              // "@<감독 이름>: <발화>"
stateNote?: string              // 휘발성 상태 — 어댑터가 제공자별 방식으로 주입
tools     : GameToolSpec[]      // JSON Schema + Zod + 엔진 스킬 핸들러 (readOnly 플래그)
onText?   : (delta) => void     // 주면 스트리밍 모드
maxTokens?
```

`GameToolSpec`은 제공자 SDK 타입을 노출하지 않고 `JsonObjectSchema`를 사용한다.
`createGameLLM(TIERS.gm|match)`가 설정의 provider를 보고 구체 어댑터를 만든다.
agents와 match-cli는 구체 SDK를 import하지 않는다.

### 제공자별 요청 조립

Anthropic:

```
tools    = tools.map(...)                                   // 프리픽스 맨 앞
system   = system.map(text => ({ type:"text", text, cache_control:{type:"ephemeral"} }))
messages = [ ...정규화된 이력(마지막에 브레이크포인트),
             { role:"user",   content: user },
             { role:"system", content: stateNote } ]         // 있을 때만
```

Gemini:

```
config.systemInstruction = system.join("\n\n")
config.tools = [{ functionDeclarations: tools.map(...) }]
config.thinkingConfig = { thinkingLevel:"MEDIUM" }
chat.history = StoredLlmHistory.messages                     // Content[] 원형
message = stateNote + "\n\n" + user
```

Gemini는 현재 턴 안에서 상태와 발화를 함께 읽지만, 반환 이력에서는 상태 부분을
제거하고 감독 발화만 저장한다. 그래서 지난 날짜·스코어가 다음 턴에 누적되지 않는다.

### 상태 스냅샷 채널

Anthropic에서는 가능하면 `messages` 끝의 `role:"system"`을 사용한다. 미지원
모델과 Gemini에서는 `상태\n\n발화`로 현재 user content에 접어 넣고 저장 전에
상태를 걷어낸다. 공통 목표는 다음과 같다.

- **캐시 보존** — 최상단 `system`을 매 턴 고쳐 쓰면 그 뒤 전체가 무효화된다.
  끝에 붙이면 앞 프리픽스가 그대로 살아 있다.
- **역할 분리** — 상태를 감독 발화에 섞으면 모델이 "감독이 자기 팀 재정을
  읊었다"로 읽는다. 오퍼레이터 채널은 그런 오독을 만들지 않는다.
- **위조 불가** — 유저 텍스트 안의 지시문과 달리 스푸핑되지 않는 경로다.

제약과 대응:

- `messages[0]`이 될 수 없고, 유저 메시지 뒤에 와야 한다 → 항상 발화 다음에 붙인다.
- Anthropic 미지원 모델은 400을 던진다 → 어댑터가 **한 번 감지하면 모델별로
  기억**하고 이후엔 폴백 형식을 쓴다.
- **이력에 남기지 않는다.** 매 턴 새로 주입되므로 누적되면 지난 날짜·지난
  스코어가 이력에 쌓여 모델을 혼란시킨다. `runTurn`이 반환 이력에서 걷어낸다.

### 도구 루프

1. 응답 `content`의 **text 블록**을 이어붙여 서사 텍스트로 누적한다.
2. 모델 메시지를 **원형(thinking/thought signature 포함)** 그대로 이력에 둔다.
3. 함수 호출이 없으면 종료한다.
4. 함수 호출마다 → `spec.handle(input)`:
   - Zod 검증 실패 → `{ ok:false, message:"입력 오류 — …" }`
   - 엔진 스킬/조회 실행 → `{ ok, message }`
   - Anthropic은 `tool_result(is_error)`, Gemini는 같은 call `id`의
     `functionResponse(output|error)`로 되돌린다 → 모델이 스스로 수정 재시도.
5. 최대 **8회 왕복**(`MAX_TOOL_ITERATIONS`). 조회 + 실행이 한 턴에 같이 도므로
   개정 전 6회에서 늘렸다. 반복마다 브레이크포인트를 직전 메시지로 옮겨 루프
   안에서도 증분 캐시가 걸린다.

### 이력 위생 (필수)

- **정규화** — 문자열 content를 텍스트 블록으로 통일한다. 어떤 턴엔 문자열,
  다른 턴엔 블록으로 같은 메시지를 보내면 프리픽스 바이트가 달라져 매 턴
  캐시가 깨진다.
- **마커 비오염** — `cache_control`은 요청용 복사본에만 붙인다. 원본 이력에
  남으면 세이브에 누적되고, 다음 턴 요청이 브레이크포인트 상한(4개)을 넘겨
  400이 된다.
- **미해결 tool_use 마감** — 턴이 `max_tokens` 등으로 끊겨 마지막 assistant에
  미해결 `tool_use`가 남으면 합성 `tool_result`(is_error)로 닫는다. 닫지 않으면
  이 이력을 재사용하는 다음 요청이 400으로 죽어 경기가 복구 불능이 된다.
- **Gemini signature 보존** — `Content.parts`의 `thoughtSignature`와 함수 호출
  위치·id를 변형하지 않는다. 공식 Chat SDK의 전체 이력을 그대로 저장한다.
- **제공자 태그** — 반환 이력은
  `{version:1, provider, model, messages}`다. 다른 provider/model로 설정을 바꾼
  진행 중 경기는 원형 이력을 섞지 않고 장부·패킷을 기준으로 이력만 새로 시작한다.
  태그 없는 배열은 이전 Anthropic 세이브로 간주한다.

### 출력 (`TurnResult`)

```
text          // 텍스트 블록 연결 (@문법 서사)
history       // 제공자·모델 태그 + 갱신된 원형 이력 — 다음 턴에 그대로 넘긴다
usage         // input / output / cacheRead / cacheWrite 토큰 누적
toolCallCount
stopReason
```

## 3. 메인 채팅 (GM 티어)

### ① 고정 — `GM_SYSTEM` 기본값 또는 어드민 오버라이드

GM의 역할, 출력 문법(@화자), 판정·반문·사실 확인·시간 진행 철칙, 진행 방식,
언어만 둔다. 조회·훈련·전술처럼 특정 스킬에만 필요한 사용법은 각 도구의
`description`으로 분리한다.

사실 확인 철칙은 다음과 같다:

> **모르는 것을 지어내지 마라.** 주어지는 것은 스쿼드 명부와 상태 요약뿐이다.
> 그 밖의 사실 — 능력치·컨디션·계약·성장, 타 팀 선수, 순위표, 일정 — 은
> 반드시 조회 도구로 확인한 뒤 답하라.

### ② 레퍼런스 — `buildGmReference(state)`

| 내용                                                             | 변경 시점                  |
| ---------------------------------------------------------------- | -------------------------- |
| 감독 프로필 (이름 · 배경 · 능력 4축 · 평판 3축 · 유저 화자 형식) | 레벨업·평판 변동           |
| 우리 팀 선수 명부 — `id\|이름\|주포지션` 전원 (30~34명)          | 이적·유스 승격·포지션 변경 |

**능력치를 일부러 넣지 않는다.** GM이 매 턴 필요한 것은 "누가 우리 팀에 있고
도구에 어떤 id를 넣어야 하는가"다. 수치는 물어볼 때만 조회하면 된다. 이 결정으로
개정 전 상위 18명 표(1,461 토큰)가 전원 명부(800 토큰)로 바뀌면서 **정보량은
늘고 토큰은 줄었다**.

### ③ 이력 — `buildGmHistory(state)`

`state.chat`에서 **텍스트만** 재구성한다(도구 호출 기록 제외). 마지막 항목은
방금 push된 이번 발화이므로 뺀다.

창은 12턴 이상 유지하되 **시작점을 6턴 단위로만 옮긴다.** 매 턴 한 칸씩
미끄러지면 프리픽스가 계속 달라져 이력 캐시가 한 번도 적중하지 않는다. 6턴
동안 시작점을 고정하면 그 구간 내내 캐시가 살아 있다.

### ④ 이번 턴 — 발화 + `buildGmStateNote(state)`

```
[상태 스냅샷 — 이 블록은 매 턴 갱신된다]
2026-07-26 (일) · 시즌 1 · 리그 1위 · 프리시즌 (개막 2026-08-15) · 여름 이적시장 열림 (~2026-09-01)
다음 경기: R1 2026-08-15 홈 vs 사우샘프턴
전술: 4-3-3 · 멘탈3 라인3 압박3 템포3 폭3 패스mixed · 선발 평균 적응 60
재정: 잔고 £120.0M · 주급 £3.42M/주 · 이적예산 £90.0M
예정 훈련 2건: 07-27 오전 세트피스 반복 / 07-28 오후 회복 러닝
주의: 부상 1 (사카 햄스트링~08-02) · 불만 1 (외데고르) · 미토마 스카우트 파견 중 — 보고 08-02
최근 사건: 07-01 여름 이적시장 개장 / …
```

감독 발화는 레퍼런스 블록의 감독 이름을 사용해 `@<감독 이름>: <원문>`으로
따로 간다. 예를 들어 감독 이름이 `김감독`이면 `@김감독: 측면을 더 적극적으로
써.`가 된다. 과거 이력의 유저 턴도 같은 형식으로 재구성한다.

### 도구 (16개 = 실행 11 + 조회 4 + 스카우트 1)

도구별 자연어 사용법은 `DEFAULT_SKILL_DESCRIPTIONS`가 코드 기본값이며,
`GET/PUT/DELETE /api/admin/skills`로 조회·편집·초기화한다. 런타임은 매 턴 현재
설명을 읽어 `GameToolSpec.description`에 넣는다. 아래 입력 스키마와 엔진 바인딩은
설명 편집과 무관하게 고정된다.

**실행 (상태 변경 — 채팅에 스킬 칩으로 기록)**

| ------------------------ | ---------------------- | ---------------------------------------------------------------- |
| `advance_time`           | `advanceTime`          | 시간이 흐르는 유일한 경로. digest를 message로 반환               |
| `start_match`            | `startMatch`           | 경기일에만                                                       |

**조회 (읽기 전용 — `readOnly: true`, 칩으로 기록하지 않는다)**

| 도구             | 엔진            | 반환                                                                           |
| ---------------- | --------------- | ------------------------------------------------------------------------------ |

| `get_player`     | `playerCard`    | 선수 카드 — 우리 팀은 전부, 타 팀은 안개 적용 + 부상·징계·이동 **이력**        |

| `get_league`     | `leagueView`    | `standings` 대회별 순위표(+최근 5경기 폼) / `fixtures` **일정 검색**            |
| `get_schedule`   | `scheduleView`  | 감독의 달력 — 경기 + **훈련 + 이적창**을 한 축에, 기본 오늘부터 14일           |
| `get_career`     | `careerView`    | **지난 시즌들**의 순위·전적·보드 평가 + 트로피·업적                            |

**조회는 "지어내기의 통로"를 막는 자리다.** 컨텍스트에 없는 사실은 전부 도구로
가야 하는데, 도구가 없으면 모델은 답할 수 없다고 말하는 대신 채워 넣는다. 그래서
공백을 메운 순서도 그 기준이었다 — 현재 배치(`get_squad`: 선수 명부엔 배치가 없고
`search_players`는 상한 15명이라 43명 스쿼드의 선발 11을 볼 방법이 없었다),
검색 풀의 범위(`search_players`의 `competition`: 좁히지 않으면 5대 리그 4천여 명이
풀이라 "리그 득점왕"의 답이 어긋난다 — 그래서 결과 헤더가 **무엇을 뒤졌는지** 밝힌다),
훈련 일정(`get_schedule`), 과거 시즌(`get_career`), 부상·경고 이력(`get_player`).

**일정은 창이 아니라 검색이다.** "가까운 N경기"만 보여주면 "다음 맨유전 언제야",
"토트넘과 지난 맞대결은 어땠지" 같은 질문에 답할 수 없고, 모델은 답할 수 없을 때
지어낸다. 그래서 `fixtures`는 조건으로 좁힌다 — `team`(기준 팀, `"all"`이면 대회
전체) · `opponent`(맞대결 + 전적 요약) · `competition` · `when`(past/upcoming/both) ·
`from`·`to` · `round` · `count`(방향별, 최대 20). 한 줄에 날짜·요일·킥오프·대회·단계·
홈원정·스코어(+득점자)가 함께 나가고, 잘린 경기 수는 항상 함께 알린다.

팀·대회 이름은 도구 입구에서 해석한다 — 약칭(맨유·스퍼스·레알·챔스), 공백 없는
표기, shortName·id를 모두 받고, 모호하면 **후보 목록을 돌려준다**(조용한 빈 결과는
모델을 창작으로 밀어낸다). `standings`도 `competition`(다른 리그·대항전 리그 페이즈)
또는 `team`(그 팀의 리그)으로 좁힐 수 있다.

⚠️ 한계: `state.matches`는 시즌 전환 때 새 시즌으로 교체되므로 맞대결 전적은
**이번 시즌**뿐이다 (지난 시즌은 `SEASON_RECORD`의 요약만 남는다). 출력에도 그렇게
명시해 모델이 과거 전적을 지어내지 않게 한다.

조회를 칩으로 남기지 않는 이유: 상태를 바꾸지 않는 호출이 채팅을 덮으면 감독이
정작 중요한 실행 칩(라인업 변경·훈련 등록)을 놓친다.

**도구 설명은 "언제 호출하는가"를 쓴다.** Opus 4.8은 도구를 보수적으로 집기
때문에, 기능 설명만 있는 description은 호출률이 떨어진다.

### 출력

- **텍스트**: `@화자:` 줄들. 후처리로 `humanizePlayerIds`가 서사에 흘러든 선수
  id를 이름으로 치환한다(유저에게 id 노출 금지).
- **도구 호출 기록**: `{ name, summary(=엔진 메시지), input }` → `chat[].toolCalls`에
  저장되고 UI가 스킬 칩으로 렌더(클릭 시 input 상세). 조회는 제외.
- **저장**: `chat`에 `{ role:"model", text, toolCalls, at: 게임날짜 }` push → `saveGame`.

### 스트리밍 · 원자성 (`runTurnLocked`)

- 게임 id별 **뮤텍스**로 턴·라인업 편집을 직렬화(저장 경합 방지).
- `onDelta` → NDJSON: `{"type":"delta","text":…}` … `{"type":"done","payload":…}`.
- GM 턴이 예외로 실패하면 **턴 시작 시점 백업(structuredClone)으로 롤백**하고
  사과 메시지만 남긴다(부분 커밋 방지).

### 클라이언트 파싱

`^@([^:]*):\s?(.*)$` 로 화자/대사를 분리, `*별표*`는 연출로 렌더. 스트리밍 중
`@화자`의 콜론이 아직 안 온 마지막 줄은 다음 델타까지 보류(파싱 깨짐 방지).

## 4. 경기 진행 (매치 캐스터 티어)

같은 3층 구조를 쓰고 내용만 갈린다.

| 층         | 내용                                                                                                                                                                                                                         |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 고정     | `MATCH_CASTER_SYSTEM` 기본값 또는 어드민 오버라이드 — 역할·출력 문법, 핵심 경기 철칙 5개(패킷·장부만 근거 · 주요 사건 기록 · 시간은 앞으로만 · 우위는 확률적 · 실제 경기 리듬), 다음 정지점까지의 진행 방식, 대화 범위, 언어 |
| ② 레퍼런스 | 감독 이름·유저 화자 형식 + **전력 분석 패킷 JSON** — 킥오프에 고정. 존 전력·매치업·키포인트·기대득점·업셋확률·라인업                                                                                                         |
| ③ 이력     | `state.pendingMatch.casterHistory` — `{provider, model, messages}`로 태깅된 제공자 원형 이력. Anthropic thinking/tool_use 또는 Gemini thoughtSignature/functionCall을 보존하며 세이브/로드 후에도 이어간다                   |
| ④ 이번 턴  | `buildLedgerNote(state)` + `@<감독 이름>: <발화>` — 주입 채널은 제공자 어댑터가 결정                                                                                                                                         |

패킷을 캐시 블록으로 올린 것이 경기 티어의 핵심 개선이다. 패킷은 3,600자
(~2,400 토큰)인데 킥오프 이후 `set_tactics`/`substitute` 때만 갱신된다. 매 턴
정가로 다시 읽을 이유가 없다. 갱신되면 ②가 한 번 무효화되지만, 그건 감독이
전술을 바꾼 순간이니 대가로 적절하다.

장부 스냅샷:

```
[경기 장부 — 매 턴 갱신]
스코어 1:0 · 28′ · first_half
홈 온필드: arsenal-raya(다비드 라야), … (id(이름) 병기)
홈 벤치: … (교체 0/5, 기회 0/3)
어웨이 온필드/벤치: …
퇴장: …                                    // 있을 때만
```

`id(이름)` 병기가 캐스터가 **서사엔 이름, 도구엔 id**를 쓰게 하는 근거다.

### 도구

GM 도구 16개 **+ `log_match_events`**. 이벤트 배열을 받아 `applyEvents`(packages/sim)가
검증한다:

- 온필드가 아닌 선수의 골/카드 → 반려
- 장부 현재 분보다 과거 → 반려
- 하드 상한: 팀당 6골, 배치당 20이벤트, 교체 5회·윈도 3회
- 반려 메시지가 `is_error`로 되돌아가 캐스터가 사건을 고쳐 재기록

### 종료 처리

장부 `phase === "finished"` 가 되면 **`finalizeMatch`가 자동 실행** — MATCH 결과
기록(**양 팀 출전 명단 포함**), 일정 엔트리 done, 출전/득점/도움/평점(SEASON_STAT ·
MATCH.result.ratings), 피로·사기·폼,
전술·포지션 적응도 상승(+GROWTH 로그), BOOKING→SUSPENSION, 경기 부상(INJURY),
홈 입장 수입(LEDGER), 평판·감독 XP, 서사 노트.

출전 명단을 남기는 이유는 스카우팅이다 — "감독이 직접 뛰는 걸 본 선수"의 유일한 근거.

## 5. 정보 비대칭 (안개)

`packages/engine/src/scouting.ts`가 단일 소스. **선수 단위** 5단계다.

| 수준       | 조건                                      | 능력치          | 잠재력          |
| ---------- | ----------------------------------------- | --------------- | --------------- |
| `own`      | 우리 팀 선수                              | 정확 (숫자)     | 구간 ±6 → ±2    |
| `adapting` | 영입 후 **정착 전** (경기·훈련으로 진행)  | ±1/±3 → 0       | 구간 ±9         |
| `scouted`  | 스카우트 리포트 완료                      | ±1/±3, 라벨만   | 구간 ±12 → ±6   |
| `seen`     | 우리와의 경기에 **실제로 출전**한 걸 봤다 | ±3 오차, 라벨만 | 구간 ±16        |
| `rumoured` | 그 외 (리그 평판)                         | ±6 오차, 라벨만 | **미지**        |

**잠재력은 누구도 단정하지 못한다** — 숫자 하나가 아니라 구간으로 답한다. 우리
선수는 출전이 쌓이면, 타 팀 선수는 스카우트를 거듭 보내면 좁아진다
(attribute-model.md §3.1).

- **지식 수준은 저장하지 않는다.** MATCH 출전 명단과 SCOUT_REPORT에서 파생한다
  (v6의 파생 우선 원칙). 벤치에만 앉아 있던 선수는 `seen`이 되지 않고, 우리가
  뛰지 않은 경기의 선수도 되지 않는다.
- **`adapting`은 날짜가 아니라 정착 진행도로 끝난다** — 경기에 내보내고 훈련을
  시킬수록 빨리 걷힌다(`settling.ts`). 영입한 선수를 빨리 알고 싶으면 쓰면 된다.
- **오차는 결정적이다.** `hash(seed, playerId, 능력치)`로 세이브 안에서 고정된
  오프셋을 만든다. 호출마다 새로 뽑으면 GM이 어제 한 말과 오늘 한 말이 달라져
  스카우팅 정보 자체를 신뢰할 수 없게 된다.
- **표현 계층 전용.** 코어(장부·판정·전력 패킷)는 언제나 참값으로 계산한다.
  관측값이 게임 상태에 반영되는 경로는 없다.
- 안개가 낀 선수에게는 **숫자를 아예 주지 않는다** — `월드클래스 / 리그 최정상 /
정상급 / 준주전급 / 리그 평균 / 평균 이하 / 약점` 라벨과 강점·약점 지목만.
  숫자를 주면 모델이 그대로 읊고 유저가 정확값으로 오해한다.
- 공개 정보는 지식 수준과 무관하게 정확하다: 이름·나이·소속·주포지션·시즌
  출전·득점·계약 만료·부상 여부.

`scout_player`로 파견하면 `SCOUT_DAYS` 뒤 tick이 완료 처리하고 다이제스트로
보고한다. 동시 파견은 `SCOUT_CONCURRENT_LIMIT`명까지.

| 출력 상한 (`maxTokens`)          | 티어 공통 64,000. **사고(thinking)와 본문을 함께 덮는 값**이라 장면 길이로 좁히면 안 된다 — 온보딩만 1,200으로 잡았다가 사고가 예산을 먹고 첫 장면이 문장 한복판에서 잘렸다. 상한은 상한일 뿐 과금은 실제 생성분이라 넉넉히 두는 데 비용이 없다. `stopReason="max_tokens"`면 온보딩은 폴백하고, 일상 턴은 이미 스트리밍된 뒤라 로그만 남긴다 |
| 사고 깊이                        | **최소.** Anthropic은 아예 끄고(`thinking: {type:"disabled"}`), Gemini는 `MINIMAL`. 서사·판정의 근거는 프롬프트와 조회 도구가 이미 쥐어 주므로 내부 추론에 예산·지연을 쓰지 않는다. 대신 사고를 끈 모델은 **추론을 보이는 응답에 흘리는 성향**이 있어, GM·캐스터 프롬프트가 "완성된 장면만, 내부 태그 금지"를 출력 문법에 함께 건다 |

## 7. 알려진 공백 (다음 마일스톤 후보)

1. **토큰 예산 상한 미구현** — usage는 관측 가능해졌지만 상한·경고는 없다.
2. **매치 티어가 도구 루프 상한을 자주 소진한다.** 실측에서 킥오프 턴이 8회
   왕복을 모두 썼다(성공 기록 3건 + 반려 재시도). 캐스터가 사건을 잘게 쪼개
   기록하기 때문인데, 반려 사유 분포를 봐야 프롬프트로 줄일지 상한을 올릴지
   판단할 수 있다.
3. **티어 분리(경기=DeepSeek)는 설정만 있고 미적용** (결정 #12). 전환 시
   `role:"system"` 폴백 경로가 실제로 쓰인다.
4. **조회 도구에 재정 상세가 없다.** 잔고·주급·예산은 상태 스냅샷에 있고 월별
   원장은 오피스 뷰에만 있다. GM이 월별 지출을 논해야 하면 도구를 추가한다.
5. **mock GM은 조회를 흉내내지 않는다.** e2e는 실행 스킬 경로만 검증한다.
