# 게임 핵심 기획 (Game Overview)

> 🚧 **초안 v0.8** · 2026-07-21 · 게임의 뼈대 — 메인 채팅 · 스킬 · 경기 시뮬레이션 · 오피스

**한 줄 요약: 게임 전체가 하나의 채팅이다.**
스토리 전개도, 경기 중계도, 팀 운영도 모두 메인 채팅에서 벌어진다. 채팅 속에서
스킬(도구)이 호출되어 팀 구성과 선수 능력치가 변하고, 경기는 능력치·전술을
근거로 LLM이 통째로 시뮬레이션하며(진행·중계·연출이 한 몸), 채팅 밖에는
명단·재정·대회·커리어를 언제든 확인하는 오피스 뷰가 있다.

| # | 기둥 | 내용 |
| --- | --- | --- |
| 1 | **메인 채팅** | 모든 스토리 전개와 경기 연출이 흐르는 단일 무대 — 감독 **롤플레이** 형식 |
| 2 | **스킬** | 선수 구성·능력치, 그리고 **시간의 흐름**까지 — 상태를 바꾸는 유일한 통로 |
| 3 | **경기 시뮬레이션** | 능력치·전술이 결과를 만드는 **LLM 통합 시뮬** — 진행·중계·연출이 한 몸 |
| 4 | **오피스** | 채팅과 별개로 상시 열람 — 팀 명단 · 달력 · 재정 · **대회**(대회별 순위·일정) · 커리어(트로피·업적) |

> 데이터 소싱은 [data-sourcing.md](./data-sourcing.md), 그 결정 근거는
> [ADR 0001](../decisions/0001-mvp-real-data-deferred-licensing.md) 참고.
> 이 문서는 "게임이 어떻게 돌아가는가"를 다룬다.

## 1. 컨셉

### 한 줄 피치

> 슬라이더와 스프레드시트 대신 **대화**로 팀을 이끈다 —
> 매 시즌이 한 편의 드라마가 되는 AI 풋볼 매니저.

### 플레이어 판타지

- 나는 감독이다. 메뉴가 아니라 **말**로 지휘한다.
- 선수들은 살아있다 — 내 말과 결정을 기억하고, 감정으로 반응한다.
- 경기 결과엔 이유가 있다. 이기든 지든 "왜"를 게임이 이야기로 설명해 준다.

### Football Manager와의 차별점

| | Football Manager | story-fm |
| --- | --- | --- |
| 인터페이스 | 메뉴·슬라이더·표 | 자연어 채팅 (+ 보조 뷰) |
| 경기 | 2D/3D 엔진 관전 | 텍스트 중계 — 하이라이트 서사 |
| 선수 | 능력치 덩어리 | 능력치 + **페르소나** (성격·기억·관계) |
| 재미의 중심 | 최적화·성취 | **서사**·관계·납득되는 드라마 |
| 결과 설명 | 스탯으로 추정 | 원인 태그 기반으로 게임이 직접 설명 |

```
        │  스토리 전개 · 경기 연출    │      │  ① 스쿼드 명단           │
        │  화자: 수석코치·기자·       │      │  ② 재정 보고서           │
        │        구단주·선수 …      │      │  ③ 대회 (순위·일정)       │
        └────┬──────────▲─────────┘      └───────────▲───────────┘
             │ 스킬 호출  │ 결과·서사                   │ 프로젝션
        ┌────▼──────────┴────────────────────────────┴───────────┐
        │              게임 코어 (결정적 장부)                       │
        │  상태(선수·팀·재정·일정) · 이벤트 로그 · 전력 분석 · 규칙 검증  │
        └─────────────────────────────────────────────────────────┘
```

### 2.1 메인 채팅 — 스토리와 경기의 단일 무대

채팅은 **롤플레이 형식**이다. 유저는 감독 한 사람을 연기하고, 모델(GM)은
나머지 세계 전부를 연기한다.

| 턴 | 내용 |
| --- | --- |
| **유저 턴** | 항상 **감독의 행동 혹은 대사** — 그 외의 것일 수 없다 |
| **모델 턴** | 세계의 응답 — 화자들(수석코치·선수·기자·구단주·중계…)의 행동·대사 + 필요한 **스킬 호출** + 장면 연출 |

**표기 규약** — 모델 턴은 세 가지 요소의 나열이다.

| 요소 | 형식 | 예 |
| --- | --- | --- |
| 행동·연출 | `*…*` (유저·모델 공통) | `*고개를 숙인다*` |
| 화자 발화 | `@화자명:` 으로 시작 (모델 턴) | `@수석코치: *고개를 숙인다* 죄송합니다...` |
| 내레이션 | `@:` 로 시작 — 화자 없는 연출 (모델 턴) | `@: *라커룸이 얼어붙는다*` |
| 스킬 호출 | **미리 정의된 함수 호출부** 생성 (모델 턴) | `team_talk({ outcome: "feared", … })` |

유저 턴에는 화자 태그가 없다 — 항상 감독 본인이므로. 모델 턴의 모든 텍스트
요소는 `@`로 시작한다(`@화자명:` 또는 내레이터 `@:`) — 파싱이 단순해진다.

```
[감독] *고함을 지르며 책상을 엎는다* 나가!!!

[모델] ⚙ team_talk({ outcome: "feared", intensity: 3 })
      @수석코치: *고개를 숙인다* 죄송합니다...
      @: *라커룸이 얼어붙는다. 몇몇 선수가 시선을 피한다*
```

> 목업의 `[감독]` `[모델]`은 문서용 턴 표시, `⚙`는 함수 호출부의 렌더링
> 표시다 — 실제 UI에선 말풍선과 스킬 카드로 구분된다.

**규칙**

- **권한 경계** — 유저는 감독 자신만 움직인다. NPC와 세계의 사실은 모델 턴만
  만든다. 유저가 `*수석코치가 사표를 쓴다*`처럼 세계를 서술하면, GM은 이를
  사실이 아니라 감독의 시도·의도로 해석해 결과를 판정한다.
- **감독의 행동도 세계에 흔적을 남긴다** — 책상을 엎으면 연출로 끝나지 않고
  GM 판정 → 스킬 경로로 사기·관계에 반영된다. 변화량은 코어 공식이
  정한다(→ §7). 극단 행동도 검열 없이 수용하되, **세계는 반드시 그에 맞게
  반응한다** — 무반응·물타기 금지 (결정 #9).
- **스킬 호출은 미리 정의된 함수 호출부로 생성된다** — 서사 텍스트에 섞인
  서술이 아니라 구조화된 호출(구현: tool call + Zod 검증, → §2.2)이며, 모델
  턴 안에 투명하게 노출된다. 무엇이 바뀌었는지 항상 보인다 (납득 가능한
  결과, 디자인 원칙 2).
- **화자는 `@태그`로 명시** — 모델 턴의 각 발화는 `@수석코치:`처럼 화자
  태그로 시작하고, 화자 없는 내레이션은 `@:`를 쓴다. 한 턴에 여러 화자가
  등장할 수 있다. 태그는 페르소나의 캐릭터 ID와 1:1로 연결되어(→ §6·§8)
  UI가 화자별 말풍선·아바타로 렌더할 수 있다. 화자는 상황에 따라
  수석코치·선수·기자·구단주·중계로 바뀐다.
- **메타 발화도 감독의 대사로 소화** — "경기일로 넘어가자" 같은 진행 요청도
  GM이 의도를 읽어 스킬(`advance_time` 등)로 옮긴다(→ §3). 대화가 얼마든지
  길어져도 세계는 멈춰 있다.

### 2.2 스킬 — 상태 변경의 유일한 통로

> **철칙: LLM의 자유 텍스트는 게임 상태를 1비트도 바꾸지 못한다.**

- 모든 상태 변경은 `스킬 호출 → Zod 검증 → 결정적 상태 전이 → 이벤트 로그
  append` 경로만 탄다. 서사는 그 결과를 읽어서 입힌 것.
- **시간도 상태다.** 캘린더 날짜와 경기 시계는 `advance_time` /
  `advance_match` 스킬로만 흐른다 — 서사가 "며칠 뒤…"라고 쓴다고 세계의
  시계가 움직이는 일은 없다.
- 플레이어의 자연어를 GM이 의도 해석해 스킬을 호출한다. 해석이 모호하거나
  규칙 위반(존재하지 않는 선수, 예산 초과, 불가능한 포메이션)이면 실행하지
  않고 **반문**한다. — "성호는 부상 회복 중인데 선발로 쓰시겠어요?"
- 스킬 목록은 §5.

### 2.3 경기 시뮬레이션 — LLM이 진행·중계·연출을 한 몸으로

- 경기는 매치 티어 LLM이 시뮬레이션한다 (결정 #14) — 코어가 만든 **전력
  분석 패킷**(능력치·전술·상성)을 근거로 사건을 결정하며 중계한다. 코어는
  생성된 사건을 검증해 장부에 기록한다. (→ §4)

### 2.4 오피스 — 채팅 밖 상시 뷰

| 뷰 | 내용 |
| --- | --- |
| **스쿼드 명단** | 선수 목록 — 능력치(숫자 그대로), 상태(폼·사기·피로·부상), 포지션, 계약(주급·만료) |
| **재정 보고서** | 이적 예산, 주급 총액, 주간/월간 수입·지출, 구단주(보드) 기대치 |
| **대회** | 대회별 탭(우리 리그 · 우리 대항전) — 순위표, 라운드별 일정과 결과, 대항전 통과선·녹아웃 브래킷 |
| **커리어** | 감독 프로필(능력치·평판) · **트로피 보관함** · 업적 · 시즌별 기록 (결정 #15) |

- 네 뷰 모두 이벤트 로그에서 파생되는 **읽기 전용 프로젝션**. 오피스에서
  조작은 없다 — 조작은 언제나 채팅에서.
- 채팅에서 "재정 어때?"라고 물어도 답해 주지만, 오피스는 대화 없이
  "지금 바로 확인"하는 용도. 스카우트 리포트는 LLM 생성물을 캐싱해 재사용.
- **숫자는 오피스에, 서술은 채팅에** (결정 #2) — GM은 채팅에서 능력치 숫자를
  읊지 않고 스카우트처럼 서술한다. "민준의 왼발 슈팅은 리그 정상급입니다."
  (서술 밴드 → attribute-model.md)

## 3. 게임 루프 — 캘린더와 시간

씬·턴 같은 인위적 단위로 진행을 쪼개지 않는다. 뼈대는 **캘린더**, 진행은
**시간 스킬**, 그 사이는 전부 자유 대화다 — 플레이어가 원하는 만큼 머물고,
원할 때 넘어간다. 세션 길이 목표 같은 것도 없다 — 유저 플레이마다 다르다
(결정 #6).

**시작과 끝** — 새 게임: EPL 20팀 중 하나를 맡고 감독 캐릭터를 직접
입력해 만든다(결정 #11, 온보딩 → [game-loop.md](./game-loop.md)). 시즌
종료: 보드 평가·에필로그·트로피가 커리어에 적재되고, **시즌 전환을 거쳐
다음 시즌으로 이어진다** (결정 #15 — 멀티시즌 코어, → game-loop.md §7).

```
캘린더 (코어 상태)
 ├─ 리그 일정 (라운드 N회)
 ├─ 이적시장 개폐 · 계약 만료일
 ├─ 주간 훈련 리듬
 └─ 동적 이벤트 (부상 발생, 이적 오퍼 도착, 구단주 호출 …)
```

### 원칙 — 시간은 스킬로만 흐른다

- 현재 날짜는 게임 코어 상태의 일부다. **대화는 시간을 흐르게 하지 않는다.**
  전술 상의, 선수 면담, 재정 질문… 얼마든지 길게 나눠도 세계는 그 시각에
  멈춰 있다.
- "다음 경기로 가자", "이틀 뒤에 보고해 줘" — 플레이어의 진행 의사를 GM이
  `advance_time` 호출로 옮긴다. 시간이 전진하는 경로는 이것뿐이다.

### `advance_time`이 하는 일 (결정적)

1. 목표 시점(지정 날짜 또는 다음 스케줄)까지 하루 단위로 tick — 훈련 진행,
   피로·부상 회복, 사기 변화, 방치된 문제의 악화를 코어 공식으로 갱신한다.
2. 캘린더·동적 이벤트를 날짜순으로 해소하되, **감독의 결정이 필요한 이벤트**
   (경기일, 이적 오퍼, 부상, 구단주 호출)를 만나면 그 날짜에서 멈춘다.
3. 지나간 기간은 GM이 다이제스트로 보고한다. 전부 나열이 아니라 서사 가치·
   시급성 기준으로 골라서 — 불만 쌓인 주전, 폼 오른 유망주, 임박한 계약 만료.

→ 방치의 비용은 자연스럽게 생긴다. 면담을 미룬 불만 선수는 tick마다 사기가
내려간다 — 별도 페널티 규칙이 아니라 그냥 시간의 결과다.

### 플레이 목업 — 주중

```
[모델] @: *화요일 아침, 사무실 문을 두드리는 소리*
      @수석코치: *훈련 일지를 내밀며* 훈련 보고입니다. 민준이 슈팅
      훈련에서 눈에 띄게 좋아요. 다만 왼쪽 풀백이 걱정입니다 — 성호가
      햄스트링 불편을 호소했습니다.

[감독] *일지를 넘겨보며* 이번 주 팀 훈련은 세트피스 위주로. 민준은 슈팅
      개인훈련 붙여주고, 성호는 무리시키지 말고 회복 프로그램으로 돌려.

[모델] ⚙ set_training_focus({ team: "set_pieces",
                             individual: [{ player: "김민준", focus: "shooting" }],
                             recovery: ["박성호"] })
      @수석코치: *수첩에 빠르게 받아 적는다* 잡았습니다. 주말 상대는
      3위인데, 저쪽 왼쪽 윙어가 리그 최고 폼이라 성호 없이 그쪽을 어떻게
      막을지가 숙제네요.

[감독] 알겠어. 더 볼 것 없으면 경기일로 가자.

[모델] ⚙ advance_time({ until: "next_match" })
      @: *금요일 저녁, 원정 호텔*
      @수석코치: 주간 정리입니다 — 세트피스 마무리가 눈에 띄게 좋아졌고,
      성호는 회복이 빨라 벤치까진 가능합니다. 내일 아침 브리핑에서
      라인업 확정하시죠.
```

## 4. 경기의 흐름

**경기는 LLM이 시뮬레이션한다 (결정 #14).** 진행·중계·연출이 한 몸 — 매치
티어 LLM이 경기를 "이야기하면서 동시에 결정"한다. 코어의 역할은 두 가지:
판단의 **근거**(전력 분석 패킷)를 주는 것과, 생성된 사건을 **검증·기록**
(경기 장부)하는 것.

| 단계 | 주체 | 내용 |
| --- | --- | --- |
| ① 브리핑 | GM (수석코치) | 상대 분석·컨디션 보고, 라인업 확인 |
| ② 지시 해석 | LLM → 스킬 | 감독의 자연어 지시 → `TacticsSpec`(Zod)으로 구조화·검증 |
| ③ 전력 분석 | **코어 (결정적)** | 유효 능력치·존 매치업·전술 상성·소화율 → **전력 분석 패킷** — LLM 판단의 유일한 근거 |
| ④ 경기 진행 | **매치 티어 LLM** | 패킷 + 경기 장부 + 지시를 근거로, 다음 정지점까지 **중계하며 사건을 결정** — 이벤트는 `log_match_events`(tool call)로 구조화 기록 |
| ⑤ 검증·반영 | **코어 (결정적)** | 이벤트 검증(시간 순증·인원 규칙·스코어 일관성) → 장부 기록 → 스탯·폼·사기·피로·재정·리그 테이블·서사 훅 갱신 |

### 능력치·전술이 결과를 만든다는 보장

결정적 엔진이 없으므로, 영향력은 세 겹으로 보장한다 (→ match-sim.md):

1. **전력 분석 패킷이 유일한 근거** — LLM은 패킷 밖 정보로 우열을 지어낼 수
   없다. 원인 태그는 패킷 항목을 인용해야 한다.
2. **코어 검증** — 불가능한 사건(퇴장 선수의 득점, 시간 역행, 비상식적
   스코어)은 기록이 거부된다.
3. **분포 모니터링** — 같은 매치업을 반복 시뮬해 전력차 대비 결과 분포를
   측정하는 밸런스 하네스. 시드 재현 대신 통계로 검증한다.

### 경기 진행 — 사전 정의된 개입 슬롯은 없다

경기 시간도 §3과 같은 원칙을 따른다: **경기 시계는 `advance_match` 스킬로만
흐른다.** 한 턴에 몇 분이 진행될지는 사전에 정하지 않는다 — 시뮬은 다음
"정지점"까지 달리고, 정지점은 경기 내용이 만든다.

**정지점 — 고정 규칙표가 아니라 GM의 연출 판단 (결정 #3)**

- 어디까지 진행하고 멈출지는 경기를 서술하는 LLM 자신의 연출 판단이다.
  가이드: 골·퇴장·부상·PK·하프타임·종료 같은 극적 순간, 흐름이 바뀌는
  지점에서 멈춰 감독에게 마이크를 넘겨라.
- 유저가 명시 지정할 수도 있다 — "하프타임까지 가", "70분까지 보자" →
  `advance_match({ until })`.

**개입 — 모든 정지점에서 자유롭게**

- 정지 중 대화는 경기 시계를 멈춘 채 이뤄진다. 지시·교체
  (`set_tactics` / `set_player_instructions` / `substitute`)는 전력 분석
  패킷에 반영되어 **다음 진행부터** 경기에 스며든다 — 재시뮬 개념은 없다.
  경기는 대화처럼 앞으로만 흐른다. 횟수 제한 없음.
- "계속"이면 다음 정지점까지, "끝까지 보자"면 종료까지 요약 중계로 달린다.

### TacticsSpec (초안)

```
formation, defensiveLine(낮음~높음), pressing(강도), tempo,
width(중앙~측면), passStyle(짧게~길게), mentality(수비적~공격적),
playerInstructions: [{ player, role, instruction }] …
```

- 필드 확정은 `match-sim.md`에서. 원칙: **감독이 말할 법한 것만 필드로 만든다.**
  자연어 지시가 스펙으로 안 떨어지면 GM이 반문해서 좁힌다.

### 납득 가능한 결과 (디자인 원칙 2)

- 모든 주요 이벤트에 **원인 태그** — LLM이 전력 분석 패킷을 인용해 부여한다.
  `{ cause: "wing_overload" }` = 패킷의 "우측 측면 우위" 항목이 근거.
- 패킷에 없는 원인의 창작은 금지 — "왜 먹혔는지/왜 뚫렸는지"의 근거가 항상
  추적 가능하다. 블랙박스 서사 금지.

### 중계 목업

```
[모델] @중계: *67′ — 오버래핑한 태호의 낮은 크로스가 니어포스트를
      가른다* 민준이 밀어 넣습니다! 1–0! 후반 들어 측면을 계속 두들긴 게
      결국 통했습니다!

      @수석코치: *환호가 가라앉기 전에 벤치 옆으로 다가온다* 지시하신
      대로 측면 과부하가 먹혔어요. 다만 태호 체력이 70분이 한계입니다.
      교체 준비할까요?

[감독] *그라운드를 향해 박수를 치다가 돌아본다* 태호 빼고 현우 넣어.
      수비 라인은 그대로 간다.

[모델] ⚙ substitute({ out: "김태호", in: "이현우" })
      @: *교체 보드가 올라간다. 태호가 박수를 받으며 걸어 나온다*
```

## 5. 상태와 스킬

상태 변경의 유일한 통로가 스킬이므로(§2.2), 카탈로그는 "게임에 어떤 상태가
존재하는가"에서 도출한다. 상태에 없는 것을 바꾸는 스킬도, 스킬 없이 바뀌는
상태도 없어야 한다.

### 5.1 상태 인벤토리 (코어)

| 영역 | 내용 |
| --- | --- |
| **시간** | 현재 날짜 · 캘린더(리그 일정, 이적시장 개폐, 계약 만료) · 경기 중: 경기 시계 |
| **선수** | 능력치 · 상태(폼/사기/피로/부상) · 계약(주급/만료) · 페르소나 — 상세 → §6 |
| **감독 (플레이어)** | 프로필 · 능력치(리더십/전술/협상/미디어) · 평판(보드/언론/선수단) · 커리어(트로피 보관함·업적·시즌 기록) — 상세 → §6 |
| **스쿼드** | 보유 명단 · 선발/벤치 · 주장 · 포메이션 · TacticsSpec · 선수별 지시 · 주간 훈련 계획 |
| **재정** | 이적 예산 · 주급 총액 · 수입/지출 원장 |
| **리그** | 테이블 · 일정/결과 · 타 팀 스쿼드(간이) |
| **경기 (진행 중)** | 스코어 · 이벤트 로그 · 그라운드 위 11명 · 남은 교체 · 퇴장/부상 |
| **시장** | 보낸/받은 이적 오퍼 · 진행 중 계약 협상 · 이적 명단 · 스카우트 리포트 |
| **관계·평판** | 감독↔선수 / 선수↔선수 관계 · 구단주 신뢰/기대치 · 언론 평판 · 서사 메모리 |

모든 상태는 이벤트 로그의 프로젝션이며(§2), 오피스 뷰(§2.4)는 이 중 일부를
읽기 전용으로 보여준다.

### 5.2 스킬 유형 — 결정 방식 4종

| 유형 | 결정 방식 | 예 |
| --- | --- | --- |
| **진행형** | 시계를 움직이고, 그 사이의 일들을 코어가 결정적으로 해소 | `advance_time` |
| **설정형** | 감독의 결정을 검증 후 그대로 기록 — 판정 없음 | `set_lineup` |
| **판정형** | 감독의 '수행'을 LLM이 판정(`{outcome, intensity}`) → 변화량은 코어 공식 (→ §7) | `team_talk` |
| **거래형** | 상대방(선수·타 구단·구단주) 페르소나가 수락/거절/역제안을 판단 → 결과 반영은 코어 | `make_transfer_offer` |
| **창발형** | LLM이 사건 자체를 생성 — 코어는 규칙 검증 후 장부에 기록 (결정 #14) | `log_match_events` |

### 5.3 카탈로그

공통 계약: **Zod 입력 검증 → 규칙 검증(존재·예산·규정·가용 시점) → 결정적
상태 전이 → 이벤트 로그 append → GM이 결과를 서사로 반영.**
표기: ✅ MVP 핵심 · 🔽 MVP 축소판 · ❌ post-MVP.

#### ① 시간 진행

| `advance_match` | 다음 정지점(또는 지정 분·종료)까지 경기 진행 — **경기 시계의 유일한 경로**. 경기일 첫 호출이 킥오프 (라인업 미확정이면 거부) (→ §4) | 진행 | 경기 | ✅ |

| `substitute` | 교체 — 남은 교체 카드 검증 | 설정 | 경기 정지점 | ✅ |

#### ⑥ 미디어 · 보드

> **회견의 자리는 코어가 열고, 질문은 기자가 쓴다** (`packages/engine/src/press.ts`).
> 경기가 끝나면 매번, 큰 이적이 확정되면 그때 회견이 열린다. 코어가 넘기는 것은
> **사실 카드**(스코어·연패·폼이 바닥인 선수·영입에 밀리는 선수)이고 질문 문장이
> 아니다 — 모델은 그 카드 밖의 사실을 묻지 못하되, 묻는 말은 자기가 쓴다.
> 효과의 폭은 회견의 `weight`(1~3)에 비례하는 코어 한도가 정한다.
> 이 구조를 선수·주장·구단주로 넓히는 설계는 [approaches.md](./approaches.md).

| 스킬 | 하는 일 | 유형 | 시점 | MVP |
| --- | --- | --- | --- | --- |
| `respond_to_media` | 기자회견 답변 — 스탠스가 평판 3축·선수 사기에 반영. `decline`이면 거절(언론 평판을 잃는다) | 판정 | 회견이 열려 있을 때 | ✅ |
| `respond_to_board` | 구단주의 요청·경고에 대응 | 판정 | 이벤트 발생 시 | 🔽 |
| `request_board` | 감독이 먼저 요구 — 예산 증액, 시간(신뢰) 요청 | 거래 | 일상 | 🔽 |

#### ⑦ 세계 운영 — *GM 전용*

| 스킬 | 하는 일 | 유형 | 시점 | MVP |
| --- | --- | --- | --- | --- |
| `apply_narrative_event` | GM이 만든 서사 이벤트의 상태 반영 — **사기·폼·관계만**, 이벤트 타입별 한도표 검증 (→ §7) | 판정 | 상시 | ✅ |
| `log_match_events` | 매치 티어가 경기 진행 중 결정한 사건들의 구조화 기록 — 시간 순증·인원 규칙·스코어 일관성 검증 (→ §4) | 창발 | 경기 | ✅ |

> ①~⑥은 감독 의도의 실행, ⑦은 GM의 세계 운영에서 호출된다. 어느 쪽이든
> 호출부가 채팅에 그대로 노출된다는 점은 같다(§2.1).

### 5.4 스킬이 아닌 것

- **조회** (명단·재정·일정 질문) — 상태를 바꾸지 않으므로 GM 컨텍스트로
  바로 답한다. 도구 왕복 없음.
- **세계 이벤트** (부상 발생, 오퍼 도착, 계약 만료 경고) — tick·시뮬의
  결정적 산출이지 스킬이 아니다. 스킬은 그에 대한 감독의 *대응*.
- **유스·스태프·시설** — MVP 제외 도메인이라 카탈로그에도 없다. post-MVP에서
  도메인째 추가.
- **새 게임 / 저장 / 불러오기** — 픽션 밖 조작은 앱 UI의 몫. 채팅에 없다.

스킬별 입력 스키마와 의도 해석(자연어 → 스킬) 설계는 `ai-manager.md`(후속).

## 6. 선수·감독 모델 (초안)

선수는 3개 층으로 표현한다. **층마다 소비자가 다르다.**

| 층 | 내용 | 변화 속도 | 소비자 |
| --- | --- | --- | --- |
| **능력치** | 6축(pace · shooting · passing · dribbling · defending · physical), overall, potential, 포지션 적성, 나이 | 느림 (주~시즌) | 시뮬 코어 |
| **상태** | 폼, 사기, 피로, 부상 | 빠름 (일~경기) | 시뮬 코어 (능력치 보정계수) |
| **페르소나** | 성격 태그, 야망·충성, 관계(감독·동료), 기억(겪은 서사 이벤트) | 서사에 따라 | LLM 에이전트 (대사·반응·서사) |

- 경기력 = `능력치 × f(상태)`. 페르소나는 시뮬 숫자에 **직접 개입하지
  않는다** — 영향을 주려면 반드시 상태(사기 등)를 거친다. 코어 vs LLM 경계가
  선수 모델 안에서도 유지된다.
- 데이터 출처: MVP는 EA FC 데이터셋 6축을 그대로 시드로 사용(🔴 라이선스
  부채), 리그·팀 구조는 CC0. → [data-sourcing.md](./data-sourcing.md) §4·§6.
- 페르소나 초기값: 실측 데이터에 없으므로 **LLM으로 1회 생성 후 고정 저장**
  (매 대화마다 생성 금지 — 일관성·비용). 상세는 [personas.md](./personas.md).
- ⚠️ 실명 선수에 가상 성격·대사를 입히는 것은 라이선스 부채(NIL)를 키운다 —
  MVP 한정으로 쓰되 부정적 실명 서사는 금지(→ narrative.md §7), 정식 출시 전
  가명 전환 필수 ([data-sourcing.md](./data-sourcing.md) §7).

### 감독 — 플레이어 캐릭터 (결정 #8 · #13)

감독은 유저가 연기하는 캐릭터이자 세계의 엔티티다.

| 층 | 내용 |
| --- | --- |
| 프로필 | 이름·배경 — 새 게임 시작 시 유저가 생성 (→ game-loop.md 온보딩) |
| **능력치** | 리더십 · 전술 · 협상 · 미디어 (0~99) — 게임 효과의 계수 (→ attribute-model.md §7) |
| 평판 | 보드 신뢰 · 언론 평판 · 선수단 신망 — 판정형 스킬 결과와 성적이 움직인다 |
| 커리어 기록 | 통산 전적 · **트로피 보관함** · 업적 · 클럽 이력 — 시즌마다 누적 (→ game-loop §7) |

- **감독의 성과 = 유저의 플레이 × 감독 능력치.** 무슨 말을 하는가는 LLM이
  판정하고, 그 말이 얼마나 먹히는가는 능력치가 정한다 — 같은 팀토크도
  리더십이 자라면 더 크게 울린다.
  - 리더십 → 팀토크·면담 효과, 선수 순응 (사기·관계 반응 폭)
  - 전술 → **전술 소화율** — 지시가 시뮬 보정으로 반영되는 강도, 분석 해상도
  - 협상 → 이적·계약 거래형 판정의 수락 문턱·조건 민감도
  - 미디어 → 기자회견 효과, 평판 변동 폭
- **능력치는 플레이로 자란다** — 잘 쓴 스킬이 해당 축의 XP가 된다 (면담
  성공→리더십, 전술 기인 득점→전술, 협상 성사→협상). 성장 공식은 코어(→ §7).
- GM은 감독을 절대 연기하지 않는다 — 유저 턴 전용 (§2.1 권한 경계).
- **커리어는 멀티시즌으로 이어진다** (결정 #15) — 트로피 보관함과 업적이
  시즌마다 쌓인다. 타 클럽 이직은 post-MVP.

## 7. 능력치·상태 변경 가드레일

> **원칙: LLM은 "무엇이 일어났는가"를 정하고, "얼마나 변하는가"는 코어
> 공식이 정한다.**

| 경로 | 트리거 | 변하는 것 | 결정 주체 |
| --- | --- | --- | --- |
| 훈련 | `set_training_focus` (주간) | 세부 능력치 미세 성장 — 나이·포텐셜 곡선 반영 | 코어 공식 |
| 경기 경험 | 출전·활약 | 폼 변동 + 미세 성장 | 코어 공식 |
| 면담/팀토크 | `talk_to_player` / `team_talk` | 사기·관계 | LLM은 대화 결과 판정만 (`{outcome, intensity}`) → 변화량은 공식 |
| 부상·회복 | 시뮬 이벤트 / 회복 지정 | 피로·부상 상태 | 코어 공식 (회복 곡선) |
| 나이 | 시즌 경과 | 성장/쇠퇴 곡선 | 코어 공식 |
| 서사 이벤트 | GM 제안 → `apply_narrative_event` | **사기·폼·관계만** — 능력치 직접 변경 금지 | 스킬 검증 (이벤트 타입별 한도표) |
| 감독 성장 | 스킬 사용 결과 — 면담·팀토크 성공, 전술 기인 득점, 협상 성사, 미디어 대응 | 감독 능력치 (해당 축 XP) | 코어 공식 — 성공은 크게, 시도는 소량 (→ attribute-model.md §7) |

- 예: 면담에서 LLM이 `{ outcome: "encouraged", intensity: 2 }`로 판정하면
  사기 +Δ는 공식이 계산. LLM이 "+5" 같은 숫자를 직접 쓰는 일은 없다.
- "각성" 같은 극적 능력치 이벤트는 **없다** (결정 #7). 능력치는 위 표의
  경로로만 변한다 — 드라마는 사기·폼·관계·서사가 만든다.
- 수치 곡선·계수 설계는 `attribute-model.md`(후속).

## 8. 서사 시스템 (개요)

- **서사 메모리**: 이벤트 로그 중 서사 가치가 있는 것에 태그를 남기고 시즌
  아크로 축적한다 — 유망주의 데뷔골, 라이벌전 설욕, 주장과의 갈등. GM은 매
  응답에서 이 메모리를 컨텍스트로 받아 "이어지는 이야기"를 만든다.
- **핵심 NPC만 깊게**: MVP는 팀 내 5~8명(주장, 에이스, 유망주, 불만분자,
  베테랑…) + 구단주 + 담당 기자만 풍부한 페르소나. 나머지 선수는 얕은 템플릿.
- 라이벌 팀·감독의 서사(악연 축적)는 post-MVP.
- 상세는 `narrative.md` / `personas.md`(후속).

## 9. LLM 티어 구조 (개요)

**방침 (결정 #12): 품질 우선 — 비용 최적화는 후순위.** 역할에 맞는 모델을 쓴다.

| 티어 | 담당 | 모델 (스냅샷 — `packages/llm` 설정이 원본) |
| --- | --- | --- |
| **GM 티어** | 메인 서사 — 일상 스토리, 의도 해석, 판정, 서사 메모리·아크 | Claude Opus 계열 |
| **매치 티어** | 경기 진행 — 중계 생성, 정지점 연출, 경기 장면 대화 | **시작은 Claude Opus** → DeepSeek V4 Pro (검증 후 전환) |

- GM은 단일 역할이고, **장면에 따라 구동 모델이 라우팅**된다 (일상=GM 티어,
  경기=매치 티어). 판정형 스킬의 판정은 장면과 무관하게 GM 티어 고정 —
  판정 기준의 일관성 (심판은 한 명).
- **멀티턴 캐시 구조는 유지** — 컨텍스트를 안정도 순서로 쌓고 프로바이더별
  캐싱(Anthropic 프롬프트 캐싱 / DeepSeek 컨텍스트 캐싱)을 태운다.
- 반복 생성물(스카우트 리포트 등)은 결과 캐싱. 상세는 [economy.md](./economy.md).
