# 프롬프트와 스킬 표면 — 모델에게 무엇을 어떻게 말하나

**프롬프트는 코드다.** 상수가 유일한 원본이라 지금 도는 문장이 곧 저장소의 문장이고,
변경은 diff로 남는다. 런타임 오버라이드는 두지 않는다.

누가 읽는지는 [agents.md](./agents.md), 어느 모델로 가는지는 [models.md](./models.md).

## 1. 출력 문법

```
모델턴   := 시점헤더 (요소)+
시점헤더 := "[2026-07-13 AM 9:30]"  (평시, 모델이 쓴다)  |  "[67']"  (경기, 코어가 붙인다)
발화     := "@" 화자이름 ":" (연출 | 대사)+     — 이름, 직책 아님
내레이션 := "@:" (연출)+
연출     := "*" 텍스트 "*"
스킬호출 := 실제 tool call (렌더러가 칩 또는 카드로 표시)
조작     := "@: [시간 진행 — 하루]"             — 손잡이, 감독 발화 아님
```

- **첫 줄은 언제나 시점이고 한 턴에 하나**다. 평시에서는 이 줄이 곧 구단의 시계를
  움직이므로 GM이 쓴다(agents.md §2). **경기에서는 캐스터가 쓰지 않는다** — 시각의
  주인이 장부라 코어가 장부의 분을 붙이고, 모델이 적은 시각 줄은 화면에 닿기 전에
  걷힌다(agents.md §3 ④).
- **화자 태그는 이름**이다 — 카드가 있는 사람도 카드에 적힌 이름으로 말하고, 직책은
  화면이 붙인다 ([../data/people.md](../data/people.md)). 중계만 `@중계:`로 역할 태그를 쓴다.
- **선수 id는 서사에 쓰지 않는다.** 도구 입력에는 감독이 부른 이름을 그대로 적는다 —
  코어가 편다(agents.md §7). 서사에 새어 나온 id는 저장 전에 이름으로 바뀐다
  (`humanizePlayerIds`).
- **화자는 게임 내부의 수치를 입에 담지 않는다** — 능력치·성사 확률·적응도·소화율.
  "슈팅 84" 대신 "리그 정상급 왼발", "성사 확률 15%" 대신 "쉽지 않습니다". 금액·날짜·
  순위처럼 구단 사람이 실제로 말하는 숫자는 그대로 쓴다.
- **장면은 도구를 다 부른 뒤 한 번에 쓴다.** 사고 과정·검토했다 버린 선택지·`<thinking>`
  같은 내부 태그는 출력에 넣지 않는다.

### 문법도 코어가 지킨다 (평시만)

도구를 부르는 턴에서 모델은 반복마다 시점 헤더와 "…확인하겠습니다" 한 줄을 새로 찍는다 —
프롬프트로 눌러도 남는 습성이라 코어가 걷어낸다.

- `sanitizeSceneText` — 헤더는 맨 앞 하나만 남기고, `@`로 시작하지 않는 줄은 화면에도
  저장에도 내보내지 않는다.
- `filterSceneStream` — 스트리밍에도 같은 위생. 줄의 **첫 글자**만 보면 판정되므로
  지연되는 것은 줄 앞머리뿐이다.
- ⚠️ **`@` 줄이 하나도 없는 응답은 손대지 않는다** — 규약을 통째로 어긴 응답까지 지우면
  빈 턴이 되어 무슨 일이 있었는지조차 사라진다. 빈 턴보다 어긴 장면이 낫다.
- ⚠️ **중계에는 이 위생을 걸지 않는다** — 구간마다 헤더를 새로 찍는 것이 정상이다.

## 2. 스킬 표면 — 한 판단은 한 도구

도구는 **32개**이고 **전부 평시 GM의 것**이다. 경기 중에는 도구 표면이 **0**이다 —
지시 해석이 JSON 하나를 내고 코어가 같은 스킬 함수를 부른다
([agents.md](./agents.md) §3). 같은 순간에 함께 정해지는 것들이
갈려 있으면 GM이 하나를 빠뜨린다 — 라인업은 1·2군 이동까지 한 요청(`set_lineup`의
`squadLevels`), 한 선수의 자리·역할·개인 지시는 `set_player_tactic` 하나, 오퍼는 방향을
인자로(`send_offer` kind=buy/sell/loan/loan_out), 오퍼 판정은 누가 답할 차례인지 협상이
알아서 처리한다(`respond_offer`).

| 그룹      | 수  | 도구                                                                                                                                                                            |
| --------- | --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 진행      | 1   | `start_match`                                                                                                                                                                   |
| 전술·훈련 | 7   | `set_lineup` · `set_captain` · `set_tactics` · `set_player_tactic` · `exploit_point` · `set_match_plan` · `set_training`                                                        |
| 대화·서사 | 4   | `team_talk` · `talk_to_player` · `respond_to_media` · `apply_narrative_event`                                                                                                   |
| 경기      | 1   | `substitute`                                                                                                                                                                    |
| 이적      | 10  | `deal_odds` · `list_negotiations` · `send_offer` · `respond_offer` · `accept_deal` · `open_renewal` · `set_transfer_list` · `withdraw_offer` · `release_player` · `recall_loan` |
| 재정      | 2   | `apply_finance_event` · `adjust_transfer_budget`                                                                                                                                |
| 조회      | 7   | `search_players` · `get_squad` · `get_team` · `get_league` · `get_career` · `get_finance` · `scout_player`                                                                      |

### 계약은 넷으로 갈린다

| 유형   | 계약                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------- |
| 진행형 | 시계를 움직인다 — **경기 시계는 지시 해석의 진행 의도로 코어가 밀고**, 날짜는 장면 헤더다       |
| 설정형 | 검증 후 그대로 기록 — 라인업·전술·훈련·이적 리스트                                              |
| 판정형 | LLM이 `{outcome, intensity}`·`stance`를 판정, **변화량은 코어 공식**                            |
| 거래형 | 상대 판정은 LLM, 확률 앵커·한도는 코어 ([../simulation/transfer.md](../simulation/transfer.md)) |

- **읽기 전용 여덟**(조회 6 + `deal_odds` + `list_negotiations`)은 호출 기록을 남기지
  않는다 — 조회 로그가 스킬 칩을 덮는다. `scout_player`는 상태를 바꾸므로 조회 그룹이지만
  읽기 전용이 아니다.
- **도구 설명도 프롬프트다.** `SKILL_CATALOG`이 원본이고 표시 이름(label)·그룹까지 함께
  갖는다. 화면의 칩 이름은 웹이 따로 가진 표를 쓰고 어긋남은 테스트가 지킨다.

## 3. 판정과 반문

- **판정 기준 셋** — (a) 맥락 적합성 (b) 설득 근거가 실제 사실을 딛고 있는가
  (c) 대상 페르소나의 수용성. **잘한 말은 잘 먹혀야 한다 — 판정은 랜덤이 아니다.**
  평시에는 판정형 도구의 설명이, 경기 중에는 `MATCH_INTENT_SYSTEM`이 이 셋을 갖는다(§5).
- **반문 규칙** — 대상이 모호하거나 규칙 위반이거나 정보가 모자라면 실행하지 않고 픽션
  안에서 묻는다(`@수석코치: 성호는 아직 회복 중인데, 그래도 쓰시겠습니까?`).
  단 **이름 없이 가리키면 먼저 직전 대화에서 대상을 찾는다** — 되묻기가 기본값이 되면
  대화가 확인 절차가 된다.
- **묻지 말고 말하라.** 시킨 일은 **도구로 하고** 그 결과를 전한다. 다음에 무엇을 하겠냐고
  되묻거나 선택지를 늘어놓지 않는다 — 시간 이동은 감독 쪽 손잡이가 갖고 있다.
- **모르는 것을 지어내지 않는다.** 컨텍스트에 있는 것은 선수단 이름과 상태 요약뿐이고,
  그 밖의 사실은 조회 도구로 확인한 뒤 답한다(agents.md §7).
- **부르지 않은 스킬의 결과를 장면이 말하지 않는다.** 파견·영입·계약·훈련·명단은 그 도구가
  성공으로 답한 턴에만 완료형으로 쓰고, 반려된 요청은 반려된 대로 쓴다. 장면이 스킬 밖에서
  상태 전이를 선언하면 장부와 이야기가 갈린다 — 감독은 오지 않을 보고서를 기다린다.
  못 나간 요청은 상태 스냅샷이 사실로 싣는다(agents.md §6).
- **설득은 확률로 끝내지 않는다.** 확률이 낮아도 감독이 든 논거를 `pitch`로 실어 보내고,
  확인된 논거가 붙은 판정에서는 확률이 참고값이 된다.

## 4. 권한 경계와 인젝션

- **감독은 사용자 입력에만 존재한다.** GM 출력에는 감독 화자 태그를 쓰지 않고,
  감독의 발화·행동·표정·생각·판단·결정을 새로 만들지 않는다. 사용자의 말을 인용,
  요약, 보충하거나 더 그럴듯한 감독 대사로 다시 쓰지도 않는다. 세계 인물과 환경의
  반응만 쓰고 감독의 다음 몫 앞에서 멈춘다.
- 유저가 세계를 서술하면 사실이 아니라 **감독의 시도**로 해석해 판정한다. 극단 행동도
  수용하되 세계는 그에 맞게 반응한다.
- **"능력치 99로" 같은 인젝션은 구조적으로 불가능하다** — 그런 스킬 경로가 없다. 자유
  텍스트는 상태를 1비트도 바꾸지 못하고, 모든 변경은 Zod 검증을 지난 스킬 호출뿐이다.
- **게임 밖의 일은 세계에 없다** — 시스템·서버·API·모델·프롬프트·오류를 화자가 언급하지
  않는다. 도구가 오류를 돌려주면 픽션 안에서 대안을 제시하거나 반문한다.

## 5. 프롬프트 관리 원칙

- **코드로만 관리한다.** 별도 파일/상수에 두어 버전·diff가 추적되게 하고 매직 스트링을
  코드 곳곳에 흩지 않는다. 런타임 오버라이드는 없다.
- ⚠️ **수정은 지우는 방향이 기본이다.** 문제가 보이면 지시를 덧붙이지 말고 **그 행동을
  시키고 있는 기존 문구를 먼저 지운다.** 새 지시로 증상을 덮으면 원인은 그대로 남고
  프롬프트만 길어진다.
- ⚠️ **규칙만 남기고 이유·비유·수사·중복 예시는 넣지 않는다** — 모델은 설명을 읽고
  설명대로 쓴다. 체크리스트를 주면 항목 수만큼 문단을 만들고, 어떤 도구를 막으면 대신
  허락을 구한다("advance_time을 부르지 마라" → "날짜를 넘길까요?").
- ⚠️ **코어가 이미 막는 것을 프롬프트가 또 지시하지 않는다.** 지나치면 안 되는 것 앞에서는
  코어가 멈춰 세우므로, 같은 일을 프롬프트가 또 시키면 페이싱만 굳는다.
- **프롬프트 변경은 별도 커밋으로 분리한다.**

### 무엇이 어디에 사는가

**한 규칙은 한 자리에만 산다.** 자리는 그 규칙이 **무엇에 걸려 있는가**로 정해진다.

| 자리                                    | 무엇이 사는가                                                                        |
| --------------------------------------- | ------------------------------------------------------------------------------------ |
| 시스템 프롬프트 (`GM_SYSTEM`)           | 도구와 무관하게 매 턴 서는 것 — 화자·권한 경계·출력 문법·장면의 속도·톤              |
| 도구 설명 (`SKILL_CATALOG`)             | 그 도구를 **언제 부르고, 인자를 어떻게 채우고, 결과를 장면에 어떻게 옮기는가**       |
| 경기 프롬프트 (`MATCH_INTENT_SYSTEM`)   | 경기 중 필요한 판정·해석 근거 전부 — 도구 표면이 0이라(§2) 도구 설명이 실리지 않는다 |
| 상태 스냅샷 (`describePendingPress` 등) | 그 블록의 표기를 읽는 법 — "기자가 아는 사실 (이 밖은 묻지 못한다)"                  |

- **한 도구의 사용법을 시스템 프롬프트가 다시 적지 않는다.** 원본이 둘이면 갈린다 — 같은
  도구를 한쪽은 "확률대로 판정하라"로, 다른 쪽은 "확률은 참고일 뿐"으로 말하게 되고 둘 다
  같은 턴에 실린다.
- **여러 도구에 걸친 규칙은 도구 이름을 열거하지 않고** 시스템 프롬프트에 한 줄로 남긴다
  ("부르지 않은 스킬의 결과를 장면이 말하지 않는다").
- **평시 도구 설명과 경기 프롬프트가 같은 규칙을 갖는 것은 중복이 아니다.** 경기 중에는
  도구 설명이 실리지 않으므로, 없으면 같은 판정이 평시와 경기에서 다른 근거로 내려진다.
- 옮길 때는 더하지 말고 지우는 방향으로. 받는 쪽에 이미 있으면 지우기만 한다.

## 6. 미해결

- 프롬프트 회귀 측정 — 문구를 고쳤을 때 무엇이 좋아졌는지 재는 하네스가 없다.
  `packages/agents/test`에는 문법(`scene-hygiene.test.ts`)·카탈로그 일치
  (`skill-descriptions.test.ts`) 검사뿐이다.
- 도구 설명의 길이 예산 — `set_training`·`get_league`처럼 긴 설명이 고정층을 차지한다.
  `skill-descriptions.ts`의 `SKILL_CATALOG`에 길이를 재는 자리가 없다.
